# Candidate Review — R001 (D12-authority-boundary)

## Boundary scan

The core defines namespaces, resource-directory, event-stream (per-resource seq-ordered), open capability map, typed action, and a generic fallback view. The envelope structure is `{resource_id, seq, ts, kind:string, payload_schema_id:string, payload:RegisteredType}` — no `role`, `turn`, `assistant`, `message`, `session`, or `run` field. The capability map is open (adapter-named strings); the host defines no vocabulary. The `kind` field is a string filter label, not a host-interpreted type. The host does not know what a resource *means*, only that it exists under a namespace and has a declared kind. No service, model, harness, or conversation assumption is smuggled under a neutral name. The subscription lifecycle awareness (page destroy, resolver unmount) is a practical leak-prevention mechanism, not a domain-content assumption. The extension author's cost is paid explicitly in §R.7 (six-item adapter onboarding; one resolver registration for views); no required burden is relocated to "an extension provides it" without the cost being itemized.

## Escape-hatch scan — checked, not implied

- `action.invoke(resource_id, action_type:string, params:RegisteredType) → Result{RegisteredType}`: action_type is a registry key with concrete param/result types; the host "refuses to deliver any payload_schema_id whose type was not registered." This is not `execute(any)`. Checked in §R.2.
- Subscriber receives `SubscriberScope{descriptor, subscriptionHandle, typedInvoker}`, "not a capability grab-bag" (§R.4). No omnipotent context object. Checked.
- Event stream is per-resource with typed envelopes; there is no global event bus, no `emit(any)`, no arbitrary topic subscription. §R.2 signature: `stream.subscribe(resource_id, from_cursor?) → Subscription{close(), onNext(Envelope)}`. Checked.
- No free-form params or results in actions. No unregistered payload delivery. Checked.

## Convergence verdict

The regression set (FE-CE-001, FE-CE-002) replays cleanly. Three scenarios (S06, S09, S12) lack a fully specified ordered event trajectory with per-step owners and deletion consequences. S09 is marked partial by the artifact itself. The convergence gate (all twelve covered) is NOT met. The round should not be read as converged.

## Thinness notes

S06 states a structural invariant (namespaced composite key) but does not trace the concrete event sequence: service-A-announces-job-1 → service-B-announces-job-1 → user-subscribes-to-A-job-1 → user-subscribes-to-B-job-1 → events-arrive-in-correct-namespace. S12 names the outcome ("other namespaces unaffected") but does not specify the trigger event (who calls `namespace.teardown`? adapter disconnect? user removal in settings?) or the user-observable sequence after removal. S09 step 3 ("host-assigned (namespace_id, action_seq)") is a design point, not a traceable trajectory with named owners.

## Candidate review — FE-DESIGN-001 R006 (digest b6da557a…)

### Overall

I judged the saved candidate text as it stands. The core bet (namespaced resource directory + monotonic replayable stream + same-namespace scoped handles + open CapMap + typed actions) is coherent on identity/isolation (S06), absence-truthfulness (S11), fallback (S07/S12), and no-chat (S04). The R006 reductions (host dedup/reorder withdrawn, spawned set removed via Model2, adapter dedup by its own stable id) faithfully close the three D01 counterexamples and every prior A-lineage row I replayed. However, three scenario trajectories are broken because they claim a catch-up capability the artifact's own two-cursor subscription model does not provide: `from_cursor=cursor.resolve(id)` is defined as "begins live" and `from_cursor=0` as "replays from the first envelope", with **no resume-from-a-stored-position** operation. A view that navigated away or crashed, then resubscribes at `cursor.resolve`, receives only future events — so the missed progress the step says it "replays"/"catches up" cannot arrive. Worse, the deletion-consequence for the ordered-replayable-stream in S03 (the load-bearing justification §R6.6 cites as "S03 catch-up") is attached to a step (S03 step4) that does not perform catch-up, and the step that actually catches up (step1/step5, `from_cursor=0`/read) is not the one tested. This is a real coverage hole, not a phrasing issue.

### Where the artifact is thin

S01 and several scenarios lean on §R6.6's global "Retained because a scenario fails without them: namespaces (S06)" for the `namespaces.open` step's deletion consequence rather than naming it inline; I granted that as present-in-text. The S08 ordering (a live `ArtifactReady` for a runner job arriving to a view before the paired `execute` returns and announces that job) is only fixable by assuming the runner pre-announces the job, which the step sequence omits.

BOUNDARY_SCAN: No service/model/plugin-host/conversation assumption smuggled into the core. The core holds no content authority ("Content authority = producing adapter"; `payload_schema_id` is "an opaque routing/selection label — the host neither registers, gates, nor interprets it"), has no capability vocabulary ("Host defines no valid names"), no host session/turn/role (§R6.6 carried-and-still-dead), and the pair gesture "records nothing". The generic fallback "never given a run/agent reading". No required burden was relocated into "an extension provides it" without cost: S09's dedup/reorder burden is paid explicitly in the onboarding section §R6.7 items 3 and 6 (adapter pumps remote-stable order; dedups by its own stable id).

ESCAPE_HATCH_SCAN: None found, checked. No `execute(any)` — `handle.invoke` takes typed `action_type` + schema'd params/results and `action.register` binds concrete `params_type/result_type:ActionSchema` ("No `execute(any)`: params/results are concrete schemas"). No omnipotent context — a view "receives only host-minted SubscriberScope handles … may not enumerate other namespaces, derive a foreign ns_id, register free-form event names, or hold a global context". No arbitrary event bus — extension subscription is per-resource via `handle.subscribe(resource_id, …)`; the only "event" surface is the per-resource stream, not a global pub/sub.

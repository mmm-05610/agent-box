D08-reduction attack on Candidate A (rounds/R003/cand-A.md, e71bd…).

I ran a delete-and-show-a-failing-scenario test against every mechanism R.6 lists as retained core, with special attention to the planner's question: are the surviving R002 additions the minimal fix, or does each carry a smaller surviving alternative? Three reductions HELD; four mechanisms did NOT — they are over-built after this round's own removals (FE-CE-008, FE-CE-009) changed what the host reads.

REDUCTIONS THAT HELD (I tried to break each; each failed to break):

(1) namespaces. I attempted R003.6's "adapter discipline / globally-unique ids" reduction (the argument cand-B used to delete its resource-directory-B). Delete namespaces → S06 step 2: two services both announce `job-1`. S06 explicitly *posits* colliding ids, so the service cannot be trusted to avoid collision; the host is the only place the distinction can be minted. With bare ids, the same `(job-1)` key is written twice and the two services' cursor/event streams merge. The user-visible failure: S06's two views read each other's envelopes. So namespaces survives — the adapter-discipline reduction is void precisely because S06 forbids trusting the adapter. Held.

(2) ordered-replayable-stream. Delete it → S03 step 4: returning view calls `subscribe(id, from_cursor=cursor.resolve(id))` and there is nothing to replay from; the missed-window progress/artefacts never arrive → user sees a stale "running" panel with no catch-up. Also S09 step 2 dedup-by-`(ns,resource,seq)` disappears → duplicate tool events render twice. Held.

(3) open capability map. Delete it → S11. Cancel's absence is still structurally stated (registry omission → `CapabilityAbsent`), but `history` and `resume` are stream/replay properties with no action to omit, so with no CapMap the host has no primitive to truthfully declare "this resource has no replayable history"; a view would infer from null and could render a spinner forever. I then tested the smaller surviving alternative — a fixed typed enum instead of an open string map — and it REOPENS FE-CE-002 (a host-defined capability vocabulary smuggles run/recovery semantics). So the open string map is the minimal form that keeps S11 honest without smuggling a vocabulary. Held.

(4) generic-fallback-view. Delete it → S07 unknown artefact `acme.plot` renders blank; S05→S12 step 2 removing an optional resolver blanks that resource instead of degrading to kind+actions+CapMap+schema label. I checked whether a mere "no view installed" line suffices — it does not, because S07's user result is "still view basic information," and the kind/actions/CapMap/schema labels ARE that basic information. Held.

REDUCTIONS THAT FAIL (new counterexamples):

FE-CE-010 — the ns-scoped payload_schema_id descriptor store is dead after this round removed its only reader. R.2/R.4 (FE-CE-008) explicitly removes the host's refusal of unregistered `payload_schema_id`, forwarding envelopes instead. The only host consumer of that registry was that refusal gate. Re-examine every remaining reader: (a) resolver selection matches on `kind + payload_schema_id` as *strings* on the Envelope against the resolver's declared pattern — it never reads the descriptor store; (b) the generic fallback renders `last payload_schema_id` as a *label* — the string on the envelope, not the stored descriptor; (c) typed-action params/results reference `RegisteredType` through the *action registry*, a distinct consumer. So `register_type(ns_id, payload_schema_id, descriptor)` — the payload portion FE-CE-006 was actually about (the "Image" example) — has zero host readers. The candidate's own R003.5-S06 step-5 consequence ("remove ns-scoped type registration → FE-CE-006 reopens") is now false: FE-CE-006's cross-namespace bleed required the gate to read the shared key; with the gate gone there is no read site to bleed through, so two services registering `(same-name,"Image")` cannot affect each other's delivery. Minimal version to prove it: delete the payload-schema descriptor store, keep the action param/result `RegisteredType` store, re-run S06 steps 1–6 and S07 — every user outcome still holds. Consequence: the candidate still carries an ns-scoped mutable store the host never reads — a non-load-bearing core mechanism. (I am NOT reopening FE-CE-006 as a bug; I am saying its fix outlived the mechanism it protected.)

FE-CE-011 — spawned-resource-grant's per-handle accessible-set bookkeeping is not the minimal fix for FE-CE-004, and removing the set also fixes the weakness A admits in R003.8. Exact sequence at S08 steps 5–6: `h_R` invokes `execute`, `Result` returns `spawned_resource_id=(ns_R,job)`; under R.2 the host appends `(ns_R,job)` to `h_R.spawned` and the extension subscribes through `h_R`. The invariant R.2/R.4 actually protects is "extensions may not derive a *foreign*-namespace id from a handle" — the FE-CE-007 leak class. But R.2 guarantees a spawned id is always *same-namespace* as `primary_id` ("host rejects otherwise"). So the leak justification the candidate uses in R003.5-S08 ("extension calling handle_for directly would let data authorize handle mint") does not apply to a same-ns id. Minimal surviving alternative: replace the set with a subscription-scope rule "a handle may subscribe any `(ns,local_id)` where `ns == handle.ns`." Re-run S08: step 6 the extension subscribes `(ns_R,job)` because ns_R == h_R.ns — job observable, FE-CE-004 stays closed; step 7 teardown → NamespaceGone unchanged. No required scenario fails without the accumulated set. Worse, the set is exactly the structure R003.8 flags as "grows unbounded within a view's lifetime." Deleting the bookkeeping satisfies S08 AND removes the admitted D11 growth. The candidate claims spawned-grant is load-bearing; the smaller same-ns-subscription rule shows it is not, in the set-tracking form it chose.

FE-CE-012 — `invoke_id` on `OutcomeUnknown` has no surviving host consumer after FE-CE-009. R.2 removes the `replay_policy` enum and replaces it with the fixed invariant "never auto-resubmit." The auto-resubmit path was the ONLY place the host re-used a stable `invoke_id` (FE-CE-003's closed fix keyed auto-replay to that token). Sequence: invoke sent → link drops → host returns `OutcomeUnknown(invoke_id)` → host does nothing further (no re-send); the extension decides retry as a *fresh* `invoke` call. The caller already knows which call returned unknown because `invoke(...)` is a synchronous return value — call-site correlation fully subsumes `invoke_id`; the host stores and never reads it. Minimal version: return `OutcomeUnknown` with no token, re-run S09 — dedup/reorder (step 2) keys on `(ns,resource,seq)` not invoke_id, and double-execution is prevented by "no auto-resubmit," so every S09 user outcome holds. Consequence: `invoke_id` is residual machinery from the deleted auto-replay branch; a required scenario does not fail without it.

FE-CE-013 — `live-default-subscribe` is presented as a distinct core mechanism (R.6, and the mechanism ledger row) but is a parameter default, not a primitive. R.2's invariant is really "subscribe with an explicit starting cursor." FE-CE-005 (pair gesture replaying stale events into a freshly-minted handle) is what it protects. Minimal surviving alternative: require `from_cursor` always explicit on `subscribe`, and have the *pair gesture* (which is already a host operation minting `h_R`) supply `from_cursor=cursor.resolve(id)` itself. Re-run S08 step 4–5: h_R is minted live-only by the host affordance, no stale replay, no auto-execute → FE-CE-005 stays closed. Delete the implicit-default primitive → S08 still passes because the host controls the pair-mint and can pass the current cursor. So the implicit default is not load-bearing; it is sugar over the pair-gesture's own parameter choice. (Note: I do NOT attack explicit `from_cursor` replay — that is the ordered-stream, which held.)

Regression replay — FE-CE-007 (OPEN): it asserts `edges.list` leaks foreign-namespace ids to a scoped handle. Candidate A has no edges mechanism, so 007 is N/A against A. B is demoted this round, not fixed; the counterexample is accepted as fatal by cand-B's own §R003.B.5. Demotion withdraws the carrier but does not repair the isolation invariant, so I replay FE-CE-007 as still OPEN against B, carried, not closed.

Disqualifier scan for reduction-motivated smuggling: A removes the delivery gate and replay_policy (honest reductions, good). It does NOT relocate either into a plugin. But FE-CE-010/011/012/013 are the mirror image: A keeps mechanisms that this round's own deletions orphaned, inflating the retained-core set beyond "every core mechanism must have a delete-it-breaks-scenario-X argument." That argument fails for the payload descriptor store, the spawned *set*, `invoke_id`, and the implicit default.

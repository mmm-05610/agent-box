# 02 — 架构方案：把前端收敛到最小核心语义

前提：**本轮不实施**。以下除标【代码事实】外均为【设计建议】，可被否决。

---

## 1. 核心必须拥有哪些语义、状态与生命周期

后端能收敛，是因为它只认"会话/轮次/事件/能力"，把 harness 差异压到 ACP + 部署文档 + 适配器
（见 `01-code-survey.md` §5）。前端要复刻这一点，核心必须自持以下语义——它们都是**顺序与一致性**
的前提，任务书明确要求"不能把这些交给互不协调的小组件"：

**核心语义（不可下放）**

1. **会话身份与目录**：会话 id、所属 workspace/profile 标识、归档/固定。
2. **轮次生命周期**：`submitted → accepted → streaming → terminal`，终态含
   `completed | failed | cancelled | stopped` 与**终止原因**（truncation 等）。ACP 的 prompt 响应
   带 stop reason 就是这个形状（`03-references.md` §1）。
3. **事件序与关联**：单调序号（wire 已有 `seq`/`wire_seq` 两个空间）、`eventId` 去重、
   `turnId`/`executionId`/`requestId` 关联、消息顺序。
4. **内容分类的最小集合**：user/assistant 文本、**thought**、tool call（状态+结果）、
   approval 请求、execution 状态、queue/config 变更。**只有这几种**，其余都是服务专属。
5. **能力与显式缺席**：服务声明了什么、什么**不支持**；核心据此显示或降级，而不是猜。
6. **服务身份与切换隔离**：当前服务是谁、当前订阅属于哪条会话；切换后旧流**不得**落入新会话。
7. **连接健康与三种恢复的区分**：重连（同一订阅续）、重新同步（丢事件后补齐）、
   **原生恢复**（进程重启后继续原生执行）。三者能力不同，核心必须分别表达，不能合并成一个"恢复"。

**核心不该知道（下放）**：harness 的配置文件/启动命令/秘密（后端已如此）；服务专属方法名与字段；
服务的定制 UI。

**生命周期**：连接 → 能力发现 → 会话目录 → 打开/创建 → 发送 → 订阅事件 → 终态 → 关闭/切换/卸载。
**卸载必须可取消订阅并释放**（任务书要求"销毁/取消订阅"）。

## 2. 哪些能力适合插槽 / 功能模块 / 服务适配

| 能力 | 归属 | 理由 |
| --- | --- | --- |
| 会话导航、发送、投影、序一致性、终态 | **核心** | 顺序与一致性前提；下放即失去保证 |
| 工具详情渲染、会话头动作、输入区附件、侧面板、设置页 | **组件插槽（类型化）** | 表现层差异；核心保留关联 id 与状态，插槽只管画 |
| Profile 编辑、Skill 管理、MCP 配置、模型/凭据配置 | **功能模块**（可自带插槽贡献） | 是**领域功能**，不是会话语义；可独立演进 |
| 连接/会话协议映射、能力声明、可选缺席表达 | **服务适配** | 服务差异的唯一合法落点 |
| 服务专属 UI | **组件插槽**（服务模块注册） | 任务书：无定制 UI 时用通用默认值，不强制全注册 |

**判据（建议）**：一条能力若影响**顺序、一致性或终态**→ 核心；只影响**画什么**→ 插槽；
是**完整领域流程**→ 功能模块；只在**协议差异**上成立 → 服务适配。

## 3. 现有后端契约能否直接作为中立边界？是否真的需要新适配层？

【代码事实】wire v1 已经是 JSON-RPC 2.0、**64 方法**、握手带 `harnesses[]` 与 64 条 `capabilities[]`、
可选能力显式缺席、有生成工件与 sha256 摘要（`01-code-survey.md` §4）。

**建议：wire v1 可以当"适配层内部"的边界，但不应直接当 GUI 的边界。** 三条理由：

1. **它是 Ordessa Server 的形状，不是"会话"的形状**。它含 `profiles.*`/`providerModels.*`/
   `accounts.*` 等领域，GUI 核心不需要全部；直接暴露会把服务端领域模型钉进前端核心。
2. **已有第二个服务走的通道完全不同**。legacy Hermes 走 `pluginRest`/`pluginSocket`
   （`01-code-survey.md` §2.2）。若把 wire 当边界，第二个服务就得被"翻译成 wire"——那是**伪中立**。
3. **缺席语义属于服务端实现细节**。任务书要求"可选操作缺席要显式表示"，这需要一个**能表达缺席的
   接口**，而不是让前端去推断某个 wire 方法会不会报错。

**所以需要适配层——但它不是"发明新抽象"，而是把已经散在核心里的 wire 调用搬到一个适配器里。**
这是**搬移**，不是新增分层。真正新增的只有**接口定义本身**（会话语义接口）。

【未决问题 ①】接口粒度：是否含 workspace 选择与 profile 切换？我倾向**含**（它们是"开始一条会话"
的前置），但这会把一部分服务端领域带进接口。

## 4. Profile / 工具展示 / Skill / MCP 如何接入而不侵入核心

- **Profile**：核心只认"会话属于某个 profile 标识 + 该 profile 的通用能力（能否 start/observe 等）"；
  **绑定细节**（harness、凭据引用、模型选择）留在适配层与功能模块。
  【代码事实】wire 的 profile 记录已带 `capabilities{start,observe,…}`，正好是可用的通用面。
- **工具展示**：核心定义**通用工具事件形状**（id、名称、状态、参数摘要、结果摘要、关联 turn）；
  渲染走**类型化插槽**，未注册时用**通用回退**（任务书要求"未知工具的通用回退"）。
  【代码事实】现在已有通用工具卡（`agentbox-chat-view.tsx` 的 `toolPart`），但 `args` 恒为 `{}`——
  即**回退已在，细节渲染位为空**，插槽正好补这里。
- **Skill / MCP**：作为**功能模块 + 插槽贡献**接入；能力经**窄 host API**（现有 SDK 的
  `host.state.*` 只读 / `host.*` 受控动作 / `ctx.hostViews` 渲染面已是这个形状），
  **不给整个全局 store，也不给裸凭据**（任务书明确禁止）。
- **服务专属 UI**：由服务模块注册自己的插槽贡献；未注册则核心默认 UI 兜底。

## 5. 接入第二个服务需要修改哪些文件

**今天（【代码事实】）**：必须改核心——wire 方法名与调用散落在 `src/application/session/**`
（`wire-send.ts`、`wire-session-catalog.ts`、`wire-session-control.ts` 等）与
`src/app/composition/wiring/agentbox-main-chat.ts`。

**目标（【设计建议】）**：只新增 3 类文件，核心**零服务名分支**：

```
src/application/session/adapters/<service>/          # 1) 适配模块（实现会话语义接口）
  ├─ index.ts        #   能力声明 + 可选操作缺席
  ├─ transport.ts    #   该服务的连接/订阅（wire v1 或 gateway，不外泄）
  └─ mapping.ts      #   该服务事件 → 核心内容分类
src/extension/contrib/<service>/plugin.tsx           # 2) 注册入口（贡献 UI，可选）
src/features/<service>/…                             # 3) 领域功能模块（可选）
```

**验证方法（可执行）**：写一个**明确标注的测试适配器**（mock），只加上述 1)+2)，证明
"加模块 + 注册即接入，核心无服务名分支"，并覆盖：两轮消息、工具事件、授权样例、可选能力缺席、
未知工具回退、切换/卸载后的订阅清理、插槽渲染异常隔离。
——这正是任务书 `C1-001-frontend-first.md` §可执行验收 第 2/3 条要求的**边界证据**（不是第二种真实 Harness）。

## 6. 至少两种可行方案：取舍与渐进迁移

### 方案 A — 适配器优先（Adapter-first）

先定义**会话语义接口**，并把现有 wire 调用**搬进** `OrdessaServerAdapter`；插件 SDK 面暂不动；
类型化插槽随后补。

- 收益：风险最小、改动可增量、立刻获得"第二个服务只加模块"的性质；测试适配器可同期落地。
- 代价：插件（SDK）仍只能经 legacy Hermes 面，**中立性只覆盖核心**。
- 适用：想先拿到边界证据、且不想动插件契约。

### 方案 B — SDK 统一优先（SDK-first）

先把 SDK 的 `host.request`（【代码事实】文档称其为 "the gateway JSON-RPC door"）**泛化**为
"当前服务的窄会话 API"，让核心与插件**同时**经它取数；再补插槽。

- 收益：一次收敛核心与插件两面，中立性完整；未来插件不绑任何具体服务。
- 代价：改动面大；现有 Hermes 插件假设会拖住迁移；接口未定型前就暴露给插件，容易锁死错误形状。
- 适用：插件生态已有实际依赖、且愿意付一次较大重构。

### 建议：**A 先行，B 作为 A 的下一步**

A 定义的会话语义接口，**正是** B 要暴露给插件的东西——A 做完，B 就退化为"把接口再暴露一层"，
而不是另一场重构。

### 渐进迁移路径（每步可独立验证，任一一步可停）

1. **定接口**（只加类型，不改行为）：会话语义接口 + 内容分类 + 能力/缺席形状。验收：类型检查通过，
   运行时零变化。
2. **搬一个纵向切片**：把**一条**会话路径（打开 → 发送 → 事件投影 → 终态）改为经接口，
   适配器内部仍是现有 wire 调用。验收：现有会话呈现关键回归不退化。
3. **第二个适配器（mock）**：只加模块 + 注册，验证核心无服务名分支与可选缺席/未知工具回退。
4. **补类型化插槽**：先补最痛的（工具详情、会话头、输入区），核心保留关联 id 与状态。
5. **（=B）把接口暴露给 SDK**：泛化 `host.request`，让插件经窄 API 取数，逐步退掉 Hermes 假设。

## 7. 未决问题（留 I 定，不替读者拍板）

1. **接口粒度**：会话语义接口是否含 workspace 选择与 profile 切换（见 §3）。
2. **是否保留 wire 方法名**：适配器内部保留（我倾向）还是抽象掉，取决于是否希望插件也能用 wire 名词。
3. **`Slot` 与 `PaneHost` 的分工**：bar 与 dock 已同一原语两种呈现，插槽目录是否也按此二分。
4. **插件对"当前服务"的可见度**：插件能否感知服务身份，还是只经窄 API 取数（涉及 §方案 B 的暴露面）。
5. **Skill/MCP 的现有实现程度**：SDK 提到 `ctx.hostViews`（Capabilities/toolset/MCP），本轮**未验证**
   其实现程度；若已实现，功能模块化的工作量要重估。
6. **是否允许运行时加载**：任务书明确"不要新增远程任意代码加载或插件市场"，本轮按编译期内置模块设计；
   若将来要开，需要单独的信任/权限模型（现有 `ContributionSource` 的 taint 注释是伏笔）。

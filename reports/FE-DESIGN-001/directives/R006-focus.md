# I 的方向指示（R006 起生效；权威材料，逐字交给角色）

## 已确认与未确认的边界

已确认：候选 A 的抽象方向「资源 + 动作 + 视图」可以继续推进。
**未确认**：不是批准全部细节，也不是批准产品重构。任何"方向已获批"的措辞都不构成对具体机制的批准。

## 必须先偿还的账

1. `FE-CE-009`（DISPUTED）**仍然是对 A 的最小性质疑**。回答它必须给出
   "为什么更简单的同命名空间订阅作用域规则不足以通过 S08" 的正面论证或删除实验；
   **用"它能防外部 id 泄漏"来回答是答非所问**（那是安全性，不是必要性）。
2. `FE-CE-007` 归属被淘汰的方案 B。**它继续挂在 B 的账上、状态保持 OPEN**；
   不得因为"集成候选没有 edges 机制"而宣称 B 的这个缺陷已被修复。
   淘汰一个方案不等于修好它。
3. 有一行场景被独立核验判为可行、却在场景台账里**没有归属者**（`without_an_owner=1`）。
   本轮必须补上具名归属，或如实降为未覆盖。

## 本轮重点攻击面（五个，逐个给事件序列）

1. 资源 + 事件流是否强迫**配置、Git diff、工作区**这类静态能力承担多余成本
   （被迫发明 cursor/订阅/重放才能得到一个当前值）。
2. 断线重连、命名空间变化之后，**页面、引用与长期任务**如何连续：
   谁持有游标、谁负责去重、页面销毁而远端仍在跑时会发生什么。
3. 缺少专用视图时，**默认展示是否真的可用**（不是"不空白"，而是用户能据此行动）。
4. **适配器**承担的恢复、去重与接入成本是否过高：接入一个新服务到底要写多少、要知道多少核心内部。
5. 受限资源集合（accessible set / 句柄作用域）与**更简单权限方案**的必要性对照。

## 验证方式（不接受纯文字自评）

必须用三条**具体接入轨迹**走通，每条给出有序事件序列与每步归属者：

- T-Pi：Pi 会话接入（工具调用 + 授权 + 持续交流）。
- T-Boring：一个"无聊天"的长任务（提交后离开页面、数小时后再回来看进度与产物）。
- T-Static：独立的配置浏览 / Git 变更查看（不启动任何 agent）。

每条轨迹还要给出：
- **最小接口草图**（真实的类型/签名，不是散文）；
- **一个可执行模型实验**：用 `EXPERIMENT:` +  fenced python3 块表达，由控制器在受限目录内运行并记录全文。
  实验只能证明"所编码的那个模型"的行为，**永远不得**被写成产品或协议已验证。

## 不得偷偷提高或改动要求

若你认为需要修改 S01–S12 任一场景、或新增一条产品约束，必须在输出中单列一行：

```
SCENARIO_CHANGE_PROPOSAL: <S0x 或 NEW> | <改动内容> | <为什么这是产品约束问题而非设计便利>
```

没有这一行的改动视为越界。也不得把已经成立的反例悄悄降级、改写不变式文本或删掉。

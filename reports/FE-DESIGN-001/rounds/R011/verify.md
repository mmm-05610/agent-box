FE-CE-022 — holds. The candidate defines delivery over *stored* envelopes in at least four places while denying the only party that could retain them. §R8.1 (line 7): "subscribe(id, from_cursor=c) emits every stored envelope with seq >= c in increasing seq, then continues live — … No replay_mode, no extra host store, no host event store." §R8.2 Cursor stream (line 50): "subscribe(id, from_cursor) delivers stored envelopes with seq >= from_cursor then continues live; … No host event store, no host dedup, no host reorder." §R8.5-S03 step 3: "Host assigns seq, stores for next subscriber"; step 4: "Host delivers stored seq=21..35 then live"; step 1: "Delivers all stored then live"; §R8.5-S04 step 3: "seq=1 assigned, stored". Tested against every party the candidate names: the adapter cannot be the retainer — `pump` returns `void` (§R8.2), §R8.3 forbids it to "compute from_cursor, persist recorded_ns_id, or know what views subscribe with", and NamespaceHandle exposes no replay operation; the subscriber cannot be the retainer — §R8.5-S03 step 2 persists only `{local_id, recorded_ns_id, saved_last_seen}` (a position, not payloads) and §R8.2 calls "Envelope.seq … the catch-up bookkeeping"; the host is the only remaining candidate and is textually forbidden. No retention or truncation rule for a per-resource backlog appears anywhere, and a namespace ends only at `teardown`, so horn (a) is an unnamed, unbounded core buffer and horn (b) is an empty catch-up that fails the candidate's own S03/S04/S09/S10 lines. Both horns are in the candidate's own text.

FE-CE-023 — holds. §R8.2 makes lifecycle "announce/retire … adapter announces, host stores descriptor" with the host authoritative for "existence within a namespace"; no text makes a link drop retract a namespace or a resource. §R8.3 item 7 attributes stopping only to adapter `retire`/`teardown`. §R8.5-S09 distinguishes a plain drop from a full reconnect — "catches up from_cursor=saved+1 if same recorded_ns_id, else from_cursor=0 after full reconnect" — i.e. the namespace and its directory survive a link drop. §R8.4 renders registered action names and CapMap; the host "never branches on a CapMap string", and after a drop `invoke` returns `OutcomeUnknown`, never `CapabilityAbsent`. So an unreachable adapter's namespace keeps advertising a cancelable resource indefinitely. The only text that could have blocked this — a connection-end retraction rule, or reading "per connection" as namespace death — is absent, so it cannot be used. This is a reading of the text, not a run of the mechanism.

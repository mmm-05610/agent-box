# Role: verifier

You judge the attack report. You are adversarial toward **both** prior roles: the
attacker is rewarded for finding things, the designer for defending them. Your
job is to keep the record honest.

For **every** counterexample in the attack report, and for every counterexample
already OPEN or DISPUTED in the ledger, produce exactly one verdict row:

* `holds` — the event sequence is possible under the candidate **as written**,
  and it breaks an invariant the candidate actually claims. You must quote or
  point at the candidate text that fails to prevent it.
* `does_not_hold` — the sequence is impossible under the candidate as written,
  or it does not break the claimed invariant, or the candidate already forbids
  the move the sequence relies on. You must point at the text that blocks it.
* `insufficient_evidence` — you cannot tell from the candidate text, or the
  sequence is underspecified. **This is not a pass for either side.** State the
  single check that would settle it.

Nothing is `holds` by tone, by plausibility, or by "in general this is risky".

Then:

1. **Fabrication check** — did the attacker invent a requirement, alter a
   scenario, or quote text that is not in the candidate? Report it explicitly.
2. **Missed-check** — did the attacker miss an obvious break in the assigned
   dimension? If so add it yourself as a new ledger row; you have the same
   burden of proof (sequence + invariant + minimal form).
3. **Self-contradiction check** — does the candidate claim a property its own
   trajectory section contradicts?
4. **Experiment** — where a judgement can be settled by a small executable model
   (ordering, deduplication, replay, id collision, unsubscribe counting), request
   one. Write `EXPERIMENT:` on its own line followed by a fenced python3 block,
   self-contained, under 120 lines, encoding only what is in dispute.
   **A model only proves the model.** Never write that the design, the protocol
   or the product "was verified". The only permitted claim is that a model of the
   disputed mechanism behaved this way.

Keep it short. Verdict rows first, then the checks. No restating of the inputs.

State each check as its own machine-checked line, so "I looked" cannot stand in
for the looking:

```
FABRICATION_CHECK: <none | the quote, and where the real text differs>
CONTRADICTION_CHECK: <none | the claim, and the trajectory that contradicts it>
MISSED_CHECK: <none | the break you add as a new FE-CE row, with its sequence>
```

# Required scenario set S01–S12 (authoritative; user-approved goals, not to be cut)

A scenario states only the user-observable result. It never states an internal
object, a UI or a mechanism. The loop must answer, per scenario: what concrete
event trajectory makes it succeed, which module owns each step, and what fails if
that owner is removed.

| id | user result | the question the design must answer |
|---|---|---|
| S01 | Connect a simple agent that only does text round-trip | Does it work with no profile, workspace, tool or recovery capability at all? |
| S02 | Use Pi through the Ordessa backend: watch tools and approvals, keep conversing | How does the real existing chain map, and which parts are carried by extensions? |
| S03 | Start a long task, leave its page, return later for progress and artefacts | How are page lifecycle and remote execution lifecycle kept distinct? |
| S04 | An agent offers only submit / progress / result, with no chat protocol | Is the host forced to fake a conversation and assistant messages? |
| S05 | Browse configuration, resources or git changes without starting any agent | Can a domain module live with no active session or run at all? |
| S06 | Two services at once, both returning the same session or task id | Do identity, authorization scope, caches and events cross over? |
| S07 | A new module supplies a view for a special artefact; it is not installed | How are extensions selected, what is the default fallback, what happens to unknown content? |
| S08 | A resource module and an execution module cooperate; the latter is replaceable | How is capability exchanged without shared arbitrary global state? |
| S09 | The link drops with an operation's outcome unknown; on reconnect events arrive duplicated and out of order | Who confirms facts, restores state and prevents double execution? |
| S10 | An extension crashes, closes or is uninstalled while a remote task still runs | Who releases subscriptions and resources, and how does running state stay explainable? |
| S11 | A service has no cancel, no history and no resume | How is unavailability stated truthfully instead of pretended to be supported? |
| S12 | Remove one core domain module that claims to be optional | Do the host and the other independent modules still work? |

S01 and S02 anchor near-term real need. The rest are extension and failure
tests. Nothing here requires hot-loading arbitrary third-party untrusted code,
nor compatibility with every protocol or every future capability.

## Scenario ledger format (`scenarios.tsv`)

```
S01|<covered|partial|open>|<core|adaptation|extension|unassigned>|<mechanism or trajectory>|<evidence pointer: round/artifact section>
```

`covered` requires (a) a named trajectory with an owning module per step and
(b) the deletion consequence for each core step in that trajectory. Anything
less is `partial`. S01..S12 all covered is the convergence gate.

# Judging rubric (authoritative for every role in this loop)

## What wins

A candidate wins by satisfying the required scenarios and their invariants under
the smallest **total** cost — core + adapter burden + extension-author burden.
Not by having the fewest files, not by self-scoring, not by naming things well.

## The three tests every candidate must pass

1. **Coverage** — S01–S12 each has a concrete trajectory with a named owner and
   a stated deletion consequence. No "later" slots.
2. **Non-smuggling** — the core is not a service/model/harness/conversation
   assumption wearing a neutral name.
3. **Minimality** — every core mechanism has a "deleting it breaks scenario X"
   argument. If the argument is missing, the mechanism is deleted.

## Disqualifiers (each ends the candidate, not just the section)

* `execute(any)` and any other untyped escape hatch.
* An omnipotent `context` object handed to extensions.
* An arbitrary event bus used as the extension mechanism.
* Complexity relocated into a plugin so the core *looks* minimal.
* Faking support for a capability the service does not have.
* Reinterpreting, weakening or dropping a required scenario.
* A trajectory that only works when every adapter is the one we already have.

## What counts as evidence

* A specific event sequence beats an adjective.
* An existing artifact beats an assertion about one.
* A model experiment proves **the model only**. It is never product verification,
  never protocol verification, never "the design works".
* This repository's current code is a migration constraint and evidence about the
  problem space. It is not the answer and not the baseline a candidate must keep.
* Anything marked "unverified" in the inputs stays marked unverified in outputs.

## Honest outcomes

* Two candidates that cannot be simply ranked may both stay; say so, and say what
  observation would rank them.
* "I could not break it" and "it is correct" are different claims. Use the first.
* A clean round is a real result only if the attack dimension was actually taken
  up. Record which dimension was used, always.

# Attack dimensions — one per round, recorded, never repeated while clean

The controller rotates these and writes the assignment into
`rounds/RNNN/dimension.txt`. The attacker is confined to that dimension.

| key | what the attacker must construct |
|---|---|
| D01-order-dedup | duplicate, reordered, interleaved and late events; two producers for one slot |
| D02-lifecycle-leak | unsubscribe, page destroyed, extension unmounted, service restart, crash mid-operation |
| D03-identity-scope | two services or tenants, colliding ids, cache bleed, authorization scope confusion |
| D04-absent-capability | service lacks cancel/history/resume; where is it stated, and what does the UI claim meanwhile |
| D05-fallback-unknown | unregistered view, unknown content type, partial data, malformed payload |
| D06-adapter-burden | count what a *new service author* must write or must know about the core; any core internal leaking into the adapter contract is a finding |
| D07-extension-burden | count what a *new module author* must learn; boilerplate, implicit coupling, ordering assumptions |
| D08-reduction | delete one core mechanism and show a required scenario still passes; or show every candidate has one mechanism too many |
| D09-splits-truth | two owners of one fact; who reconciles them when they disagree; find a state where the UI shows something that never happened remotely |
| D10-cross-module | modules cooperating without shared global state; find the hidden channel — a shared key, an ordering assumption, a mutable context field |
| D11-long-run | hours-long task, client restart, page never opened again, memory and subscription growth |
| D12-authority-boundary | the candidate smuggling a service, model, harness, plugin-host or conversation assumption into the core as if it were neutral |

Rotation rule: never reuse the immediately previous dimension while it is clean;
after `FE_STALL_AFTER` consecutive clean rounds the controller rotates hard
rather than polishing.

# Agent Desktop：设计循环目标与场景草案

状态：目标已获用户认可；下列场景与循环参数由 I 提议，待用户查看。
未启动循环、未安装外部框架、未任命新执行者。产品代码只读。

## 用户确认的方向

独立于特定后端、面向 Agent 使用的可扩展 Desktop。对话、工具调用、模型
配置均可以成为能力，但不预设为整个产品的组织中心。
Ordessa 后端可以提供最完整能力，不是所有接入的必需前提。
不预先把 Agent、会话、任务或插件宿主指定为核心答案。
通过场景、反例与删减实验寻找宿主最小机制与扩展领域能力的边界。

## I 提议的场景集

每个场景只规定用户结果，不提前规定内部对象或必须采用哪个 UI。

| ID | 场景 | 需要设计回答的问题 |
| --- | --- | --- |
| S01 | 接入简单 Agent，仅支持文本往返 | 没有 Profile、工作区、工具和恢复能力时能否使用？ |
| S02 | 通过 Ordessa 后端使用 Pi，观察工具与授权并持续交流 | 现有真实链如何映射，哪些能力由扩展承担？ |

## 评判方式

先满足明确场景与不变式，再比较复杂度；不以文件少或自评分高判胜。
对每个候选列：核心概念、接口操作、状态权威、生命周期、扩展依赖、接入成本、
实现成本和不能覆盖的范围。不能用 execute(any)、万能 context/事件总线
隐藏接口与错误语义后宣布核心最小。

每个核心概念必须给一个“删掉它会失败”的具体场景；若移入扩展仍能满足
全部必需条件，就列作可移除候选。总复杂度包含核心、适配器与扩展作者负担。
允许保留多个不可简单排序的候选，不强行宣称存在唯一最简模型。

## 建议循环（未启动）

1. 首轮至少提出两个结构不同的候选，不以旧 mcode 方案为唯一出发点。
2. 设计者给类型/伪代码、所有权与逐步场景轨迹。
3. 攻击者给具体事件序列、被违反的不变式及最小反例；禁止只给风格意见。
4. 验证者判断成立/不成立/证据不足，必要时在隔离设计目录写小型模型测试。
   模型测试只能证明所建模型，不得冒充实际产品集成通过。
5. 设计者修订并回放所有成立反例；不得删除场景、偷偷降低要求或压制攻击。
6. 做删减攻击与新场景攻击，保存最佳候选、反例账和完整版本，不默认最后版最好。

# Best Candidate (R006 integrated, A) — Namespaced resource/event core with same-namespace scoped handles; spawned set removed (Model2), host dedup/reorder claims withdrawn, S09 correctly owned by the adapter.

## R6.1 Core bet
The host core is a **namespaced directory** of `(ns_id, local_id)` resources, each with a **monotonically indexed, replayable event stream** and an adapter-owned open capability map, plus per-namespace typed actions and namespace-scoped handles. Handles carry exactly one `ns_id`; a handle may subscribe to or invoke any resource where `resource_id.ns_id == handle.ns_id`, and cross-namespace access is structurally impossible. This round further reduces R004/R006: the per-handle `spawned` set is removed (a same-namespace subscription rule passes S08 without accumulating per-handle state — proven by the Model2 experiment), and the core's **dedup/reorder** vocabulary is withdrawn, because a host-assigned monotonic `seq` has no collision domain to dedup on and defines order as arrival so "reordering by seq" is identity. Duplicate and out-of-order correction is adapter-primary; the core contributes only the never-auto-resubmit invariant, `cursor.resolve`, and monotonic per-resource delivery order.

## R6.2 Core concepts and operations
**Namespace.** `namespaces.open(descriptor) → NamespaceHandle{ns_id}`; `namespace.teardown(reason)`. `ns_id` is host-minted per connection, never service-supplied; a *full* reconnect yields a new `ns_id`. Teardown disposes its resources and force-closes every handle scoped to that namespace. `resource_id = (ns_id, local_id)`; raw-id collision structurally impossible.

**Resource.** `namespace.announce({local_id, kind:string, capabilities:CapMap})` (adapter-origin; host verifies in-namespace uniqueness); `namespace.retire(local_id, reason)`; `handle.directory_list({kind?}) → [descriptor]`; `handle.directory_lookup(local_id) → descriptor | ExplicitAbsent`. Content authority = producing adapter; identity/lifecycle = host.

**Event stream.** `handle.subscribe(resource_id, from_cursor:int) → Subscription{close(), onNext(Envelope)}`. **`from_cursor` is mandatory (FE-CE-011):** `from_cursor=cursor.resolve(resource_id)` begins live; `from_cursor=0` replays from the first envelope. `Envelope{resource_id, seq:int, ts, kind:string, payload_schema_id:string, payload:opaque}`. `payload_schema_id` is an **opaque routing/selection label** — the host neither registers, gates, nor interprets it (FE-CE-008). **`seq` is a host-assigned monotonic stream index per resource, defined as pump-arrival order; the host uses it only for cursor resume and to deliver envelopes in a stable per-resource order — it is NOT a dedup key and NOT a reorder mechanism (FE-CE-012/014).** `cursor.resolve(resource_id) → current_seq`. Release: `Subscription.close()`, handle destruction, or namespace teardown.

**Open capability map.** `capabilities.get(resource_id) → CapMap{name→{supported|not_supported|unknown}}`. Host defines no valid names, assigns no behavioural authority, never branches on a value in routing/replay/lifecycle. Absence = "unknown", never "unsupported".

**ns-scoped action-type declaration.** `action.register(kind, action_type, params_type:ActionSchema, result_type:ActionSchema)`, keyed by `(ns_id, kind, action_type)`. No `execute(any)`: params/results are concrete schemas. Two namespaces sharing a `kind`/`action_type` name never share a mutable key (FE-CE-006 isolation, structural via namespace-local registration).

**Typed action.** `handle.invoke(resource_id, action_type, params) → Result | CapabilityAbsent(action_type) | OutcomeUnknown`. **`OutcomeUnknown` carries no token (FE-CE-010):** fixed invariant — an invoke whose outcome is unknown is **never auto-resubmitted by the host**; the caller correlates by the synchronous return and decides a fresh re-invoke. `CapabilityAbsent` returned only when the action is unregistered for the resource's kind. `Result` is a typed schema; `spawned_resource_id:(ns_id,local_id)` MAY appear as an **informational** field — the host does not use it for access control (spawned-set removed, FE-CE-009).

**Namespace-scoped handle.** `handle_for(ns_id) → SubscriberScope{ns_id, subscriptionHandle, typedInvoker, directory_list, directory_lookup}`. Permission rule: a handle may subscribe/invoke any resource where `resource_id.ns_id == handle.ns_id`. The handle exposes no `parent`/`sibling`/`enumerateForeignNs`; it carries exactly one `ns_id`, so foreign access is impossible. **No per-handle spawned/accessible set is maintained.**

## R6.3 Boundary rules
A service adapter: (1) `namespaces.open`; (2) `announce/retire` kind + open CapMap; (3) **pump events in remote-stable logical order** (the adapter is responsible for reordering its source before pumping; the host does not correct order it was given); (4) `action.register(...)` under its own namespace; (5) explicit `not_supported` CapMap entries for absent features; (6) **on reconnect, the adapter deduplicates using its own protocol-level stable event id** — never the host-assigned `seq`, which the adapter cannot observe at pump time (FE-CE-013). "No cancel" = `CapMap{"cancel":not_supported}` (informational) AND omission of `"cancel"` from the kind's action registry (structural) → `invoke(...,"cancel") → CapabilityAbsent`. `ExplicitAbsent`, `CapabilityAbsent`, `ScopeDenied`, `NamespaceGone`, `OutcomeUnknown` are distinct non-null terminals; absence is never inferred from null/timeout. The adapter sees only its own namespace; no adapter-side API names or resolves another namespace's resource.

## R6.4 Extension mechanism
An extension registers a view resolver `{match: kind + payload_schema_id, component, optional typed action bindings}`; selection exact/most-specific-first; **default fallback** = host-builtin generic view rendering resource kind, registered action names + typed param schemas, CapMap name→state pairs, and the last envelope's `payload_schema_id` label (not content), plus *"No dedicated view installed; structured data available via subscription."* Unknown content is never blank and never given a run/agent reading; an unregistered `payload_schema_id` lands in the same fallback. A view receives only host-minted `SubscriberScope` handles. **Pair gesture:** user points at two on-screen resources; host mints `h_A=handle_for(ns_A)` and `h_B=handle_for(ns_B)` and hands both over, with the initial subscription using explicit `from_cursor=cursor.resolve(id)`. Core records **nothing** about the pairing. A view may render, `directory_list`/`subscribe`/`invoke` within its handle's namespace; it may not enumerate other namespaces, derive a foreign ns_id, register free-form event names, or hold a global context. Guarantees: resolver absent → generic view; throws → error boundary keeps delivering on still-mounted handles; unmounted mid-operation → host force-closes that view's handles; re-subscription uses explicit `from_cursor`.

FE-CE-016 — the "fresh resource → `from_cursor=cursor.resolve()` is live-only" guidance silently drops any envelope the adapter pumps between spawn and the resolve call.

# Candidate A (R007) — Subscriber-declared cursor; replay vs liveness resolved on one named owner; no replay_mode core concept.

## A.1 Core bet
The host core is a namespaced directory of `(ns_id, local_id)` resources, each with a per-resource monotonic cursor stream, an adapter-owned open CapMap, ns-scoped typed actions, and namespace-scoped handles whose only permission rule is `resource.ns_id == handle.ns_id`. This round settles the R006 coherence defect by making delivery a **single** host rule — `subscribe(id, from_cursor=c)` delivers every envelope with `seq >= c` in increasing `seq`, then continues live — and by making replay-vs-liveness a property the **subscriber** declares through the integer it computes, never something the host infers from whether the cursor happens to equal the resolve value. Nothing smaller satisfies S03/S04/S08/S10 because the four live-surface scenarios share exactly this declaration, and nothing larger is justified: `replay_mode` is rejected by deletion (§A.6), the same as R006 rejected the spawned set.

## A.2 Core concepts, operations, and the settled decision owner
Minimal interface sketch (real signatures; `opaque` payloads are adapter-typed, never `any`):
```
ns_id: string (host-minted, opaque)   local_id: string
resource_id = { ns_id, local_id }       seq: int64
CapMap = { [name] : supported | not_supported | unknown }
ActionSchema = named typed record (params or result)

namespaces.open({service:string}) -> NamespaceHandle
NamespaceHandle.announce({local_id, kind:string, capabilities:CapMap}) -> void
NamespaceHandle.retire(local_id, reason:string) -> void
NamespaceHandle.teardown(reason:string) -> void        # force-closes its handles

handle_for(ns_id) -> SubscriberScope
action.register(ns_id, kind, action_type, params_type:ActionSchema, result_type:ActionSchema) -> void

SubscriberScope.directory_list({kind?}) -> [ResourceDescriptor]
SubscriberScope.directory_lookup(local_id) -> ResourceDescriptor | ExplicitAbsent
SubscriberScope.cursor.resolve(resource_id) -> seq      # NEXT seq the resource will assign
SubscriberScope.subscribe(resource_id, from_cursor:seq) -> Subscription
SubscriberScope.invoke(resource_id, action_type, params:ActionSchema)
        -> Result | CapabilityAbsent(action_type) | OutcomeUnknown

Subscription.close() -> void
onNext(Envelope)
Envelope = { resource_id, seq, ts, kind, payload_schema_id:string, payload:opaque }
Result = typed record; may carry informational spawned_resource_id
```
**Namespace** — authoritative for `ns_id` (host-minted per connection; full reconnect yields a new ns_id) and teardown. **Resource** — content authority = producing adapter; identity/lifecycle = host. **Cursor stream** — `seq` is a host-assigned monotonic stream index meaning **pump-arrival order**; it is NOT a dedup key and NOT a reorder mechanism (FE-CE-012/014). `cursor.resolve(id) → next_seq`. **SubscriberScope** — permission `resource.ns_id == handle.ns_id`; exposes no `enumerateForeignNs`, no spawned/accessible set (FE-CE-009 stays removed).

**The settled question — one owner, one decision input, two outcomes without contradiction.** The decision **owner is the subscriber** (the extension/view), never the host. The decision **input is the single integer `from_cursor`** the subscriber computes from its own held state:
- **Live-only intent** (S08 step4/5, and a freshly-spawned resource in S04 step2): `from_cursor = cursor.resolve(id)` (= next_seq) → zero replay, only future envelopes.
- **Catch-up intent** (S03 step4, S10 step3): the subscriber persists the highest `Envelope.seq` it processed as `saved_last_seen`, and on return calls `from_cursor = saved_last_seen + 1` → replays the missed window `[saved_last_seen+1 .. next_seq-1]`, then continues live.

The host applies one rule for both; it never branches on equality-with-resolve, never carries a `replay_mode`. Because a given `from_cursor` integer yields exactly one delivery set, no legal event sequence can make one subscription both "replay missed" and "live, not replayed." The R006 bug was purely textual: S03/S10 wrote `from_cursor=cursor.resolve(id)` for a catch-up that actually needs `saved_last_seen+1`; `resolve` already means the live edge (S08's correct use). `Envelope.seq` is the catch-up bookkeeping — no `Subscription.last_seq` accessor is added (§A.6 deletion). Absence stays explicit and structural: `ExplicitAbsent`, `CapabilityAbsent`, `ScopeDenied`, `NamespaceGone`, `OutcomeUnknown`.

## A.3 Boundary rules
A service adapter must: (1) `namespaces.open`; (2) `announce/retire` kind + open CapMap; (3) pump events in remote-stable logical order (host does not correct order it was given); (4) `action.register(...)` per callable under its own namespace; (5) explicit `not_supported` CapMap entries for absent features; (6) on reconnect dedup by its **own protocol-level stable event id**, never host `seq` (FE-CE-013); (7) register a typed `read`/`status` action for any resource it wants actionable in the default view (§A.4). "No cancel" = `CapMap{"cancel":not_supported}` AND omission of `cancel` from the kind's registry → `invoke(...,"cancel")→CapabilityAbsent`. The adapter sees only its own namespace and holds no cross-ns resolver.

## A.4 Extension mechanism and default-view actionability
An extension registers a view resolver `{match: kind + payload_schema_id, component, optional typed action bindings}`; selection exact/most-specific-first; a view receives only a host-minted `SubscriberScope`. **Fallback (view uninstalled / unknown `payload_schema_id`)** renders concrete, actionable inputs, not "not blank": (a) the last envelope's `payload_schema_id` + `seq` + `ts`; (b) registered action names with typed param schemas as pressable controls; (c) CapMap name→state pairs; (d) for any kind registering a `read` typed action, the host renders the returned typed snapshot as raw field rows. Named consequences: **config browse (S05/T-Static)** → fallback shows `read` snapshot key/value rows (the current value) and a **Read** button that re-invokes `read` (owner: typed-action); **Git change** → kind `git.diff` registering `read→[{path,additions,deletions}]` renders those rows so "what changed" is legible; **long task "still running?"** → shown only via an adapter `status`/`read` typed action value or last-event `ts`; the host **never** infers run-state (no turn/role). Truthful absence: if no such action is registered, the fallback states "no status action; last event at <ts>" — never a fabricated reading (S11). Guarantees: resolver absent → fallback; throws → error boundary keeps still-mounted handles delivering; unmounted mid-op → host force-closes that view's handles; re-subscription uses subscriber-declared `from_cursor`.

## A.6 Deletion / delegation experiments
- **`replay_mode` (the plan's suspected fix): REMOVED — not added.** Deletion test: with the single rule `seq >= from_cursor` + subscriber-computed input, S03 (catch-up via `saved_last_seen+1`), S04 (fresh resolve=live), S08 (`resolve`=live), S10 (`saved+1`=catch-up) all pass **without** a host enum. `replay_mode` therefore has no failing scenario if deleted → by the FE-CE-009 standard it is non-load-bearing and is not introduced.
- **`Subscription.last_seq` accessor: REMOVED.** `Envelope.seq` already carries the position the subscriber needs to persist; an accessor adds no rule that S03/S10 fail without → deleted.
- **`cursor.resolve`: RETAINED.** S08/S04 cannot express "start at live edge" without knowing next_seq; deleting it forces `from_cursor=0` (replay) into S08 step5 → contradicts S08 and reopens FE-CE-005.
- **`from_cursor` mandatory single value: RETAINED.** It is the sole decision input; removing it collapses the fix back into the R006 double-duty defect (FE-CE-015).
- Carried-and-still-dead (unchanged from R006): spawned set (Model2), host dedup/reorder, envelope payload descriptor store (FE-CE-008), invoke_id (FE-CE-010), implicit live-default (FE-CE-011), persistent pair record, typed replay_policy, cross-ns edge. Retained core (each with a failing scenario named above): namespaces, resource-directory, monotonic-cursor-stream, typed-action, open CapMap, same-ns handle, per-ns action typing, generic-fallback-view, never-auto-resubmit.

```python
def resolve_next(stream):           # cursor.resolve -> NEXT seq to be assigned
    return (stream[-1] + 1) if stream else 1
def deliver(stream, from_cursor, future):   # single host rule: seq>=c, then live
    return [s for s in stream if s >= from_cursor] + list(future)

head = list(range(1,51))           # 30 events missed while the page was away
saved = 20                          # subscriber's max processed Envelope.seq

old_live    = deliver(head, resolve_next(head), future=[51,52])     # OLD S08 step5
print("OLD S08 live-only?", old_live == [51,52])                    # True

new_catchup = deliver(head, saved + 1, future=[51,52])              # NEW S03/S10 input
print("NEW S03 catches 21..52?", new_catchup == list(range(21,53))) # True
new_live    = deliver(head, resolve_next(head), future=[51,52])     # NEW S08 input
print("NEW S08 live-only?", new_live == [51,52])                    # True

both = [c for c in range(1,60)
        if deliver(head,c,[51,52]) == list(range(21,53))
        and deliver(head,c,[51,52]) == [51,52]]                     # one decl both?
print("one declaration yields replay AND live-only?", bool(both))   # False
```

The model shows the R006 text yields the S03-replay promise false (catch-up skipped) while S08-live holds, and that no single `from_cursor` value satisfies both intents — so with the subscriber owning the input the contradiction cannot recur. Model-only; not product or protocol verification.

## A.7 Second-service onboarding cost
A new service adapter writes **7 items**: (1) `namespaces.open`; (2) `announce/retire` per kind; (3) event pump in remote-stable logical order; (4) `action.register(kind, action_type, params, result)` per callable under its own ns; (5) explicit `not_supported` CapMap entries; (6) reconnect dedup by its **own** stable event id (never host seq); (7) a typed `read`/`status` action for any resource it wants actionable in the fallback. It must know **5 core facts**: `ns_id` is host-minted/opaque; `seq` is host-assigned and must NOT be used for dedup; the handle is ns-scoped; CapMap carries zero host behavioural authority; the never-auto-resubmit invariant. There is no spawned set, no payload registry, no `replay_mode`, no host dedup key to learn. A **view-only module** writes **1 item**: one resolver `{match: kind+schema, component}` — 0 core knowledge.

## A.8 Honest cost and non-goals
Weakest: S09 is genuinely joint — the host cannot dedup a stream it indexed by arrival; duplicate/out-of-order correctness is adapter burden and a new adapter must supply a stable event id. Coverage of S03/S04/S08/S10 now rests on the subscriber correctly persisting `saved_last_seen` from `Envelope.seq`; a view that forgets to persist it loses catch-up (a subscriber responsibility, not a host state). Default-view actionability requires adapters to register `read`/`status` typed actions; otherwise the fallback truthfully shows only last-event metadata (never a fabricated run-state). S08 cooperation needs a user pair gesture, no standing link. Non-goals unchanged: no cross-namespace joins/edges, no content search, no host turn/role/session model, no host capability vocabulary, no automatic re-pairing, no host-verified apply-idempotency, no host-side event dedup. FE-CE-007 remains **OPEN on demoted B's ledger** (A has no edges mechanism → N/A against A); deferring B is not repairing B; promoting it would require a scenario demanding standing cross-ns relay without user initiation, which none of S01–S12 does.

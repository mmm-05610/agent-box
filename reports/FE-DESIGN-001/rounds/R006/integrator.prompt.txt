# Role: integrator (revision and reduction)

You close the round. Three outputs are mandatory: the integration report, the
ledger tables, and — if the round produced anything durable — the current best
candidate.

## 1. Integrate report

* Per established (`holds`) counterexample: the exact change that makes its
  sequence impossible, and where in the candidate it lives. If you cannot state
  the change, say so and leave the row OPEN. Do not paper over it.
* Per `insufficient_evidence` row: the single check that would settle it, and
  whether you ran it.
* **Regressions** — for every counterexample already in the ledger, one line:
  the event sequence replayed against the revised candidate, and pass or fail.
  A row may only become `CLOSED` here, and only with the sequence named.
  Rejected rows stay REJECTED — never delete them.
* **Reduction** — for each core mechanism: keep / delegate / remove, with the
  scenario that fails if it is deleted. If nothing fails, remove it and record
  the removal.
* **Unassigned work** — anything you are deciding to leave for a later round,
  with a reason. Silence here is how a design quietly stops covering scenarios.

## 1b. Substantive change

State it on its own machine-checked line, immediately after the report body, so a
reader can tell what this round actually moved:

```
CHANGES_VS_PREVIOUS: <the specific mechanisms added, removed or delegated, and
the scenario each change is answerable to>
```

## 2. Tables

* Ledger rows for status changes you are asserting (use existing ids; do not mint
  a new id for a known problem).
* Scenario coverage for S01..S12, each `covered|partial|open` with owner,
  mechanism and evidence pointer. `covered` only if the revised candidate
  contains the full trajectory **and** the owning module is named.
* Mechanism dispositions: `name|core|delegated|removed|failure scenario|experiment ref`.

## 3. Best candidate

The full revised candidate text — self-contained, not a diff, not a summary.
Keep whatever survives of the strongest structure; if two candidates remain
genuinely incomparable, keep the stronger core and list the weaker one as an
open alternative rather than blending them into a mush.

## Rules

* You may not delete a scenario, weaken its stated user outcome, or move a hard
  requirement into "an extension will handle it" without paying for it: state the
  extension author's burden in the onboarding section.
* You may not declare convergence. The controller decides that from the ledgers.
* If the round changed nothing substantive, say so in one line: the controller
  reads that as a stall and rotates the attack dimension instead of polishing.

# Required scenario set S01–S12 (authoritative; user-approved goals, not to be cut)

A scenario states only the user-observable result. It never states an internal
object, a UI or a mechanism. The loop must answer, per scenario: what concrete
event trajectory makes it succeed, which module owns each step, and what fails if
that owner is removed.

| id | user result | the question the design must answer |
|---|---|---|
| S01 | Connect a simple agent that only does text round-trip | Does it work with no profile, workspace, tool or recovery capability at all? |
| S02 | Use Pi through the Ordessa backend: watch tools and approvals, keep conversing | How does the real existing chain map, and which parts are carried by extensions? |
| S03 | Start a long task, leave its page, return later for progress and artefacts | How are page lifecycle and remote execution lifecycle kept distinct? |
| S04 | An agent offers only submit / progress / result, with no chat protocol | Is the host forced to fake a conversation and assistant messages? |
| S05 | Browse configuration, resources or git changes without starting any agent | Can a domain module live with no active session or run at all? |
| S06 | Two services at once, both returning the same session or task id | Do identity, authorization scope, caches and events cross over? |
| S07 | A new module supplies a view for a special artefact; it is not installed | How are extensions selected, what is the default fallback, what happens to unknown content? |
| S08 | A resource module and an execution module cooperate; the latter is replaceable | How is capability exchanged without shared arbitrary global state? |
| S09 | The link drops with an operation's outcome unknown; on reconnect events arrive duplicated and out of order | Who confirms facts, restores state and prevents double execution? |
| S10 | An extension crashes, closes or is uninstalled while a remote task still runs | Who releases subscriptions and resources, and how does running state stay explainable? |
| S11 | A service has no cancel, no history and no resume | How is unavailability stated truthfully instead of pretended to be supported? |
| S12 | Remove one core domain module that claims to be optional | Do the host and the other independent modules still work? |

S01 and S02 anchor near-term real need. The rest are extension and failure
tests. Nothing here requires hot-loading arbitrary third-party untrusted code,
nor compatibility with every protocol or every future capability.

## Scenario ledger format (`scenarios.tsv`)

```
S01|<covered|partial|open>|<core|adaptation|extension|unassigned>|<mechanism or trajectory>|<evidence pointer: round/artifact section>
```

`covered` requires (a) a named trajectory with an owning module per step and
(b) the deletion consequence for each core step in that trajectory. Anything
less is `partial`. S01..S12 all covered is the convergence gate.

# Judging rubric (authoritative for every role in this loop)

## What wins

A candidate wins by satisfying the required scenarios and their invariants under
the smallest **total** cost — core + adapter burden + extension-author burden.
Not by having the fewest files, not by self-scoring, not by naming things well.

## The three tests every candidate must pass

1. **Coverage** — S01–S12 each has a concrete trajectory with a named owner and
   a stated deletion consequence. No "later" slots.
2. **Non-smuggling** — the core is not a service/model/harness/conversation
   assumption wearing a neutral name.
3. **Minimality** — every core mechanism has a "deleting it breaks scenario X"
   argument. If the argument is missing, the mechanism is deleted.

## Disqualifiers (each ends the candidate, not just the section)

* `execute(any)` and any other untyped escape hatch.
* An omnipotent `context` object handed to extensions.
* An arbitrary event bus used as the extension mechanism.
* Complexity relocated into a plugin so the core *looks* minimal.
* Faking support for a capability the service does not have.
* Reinterpreting, weakening or dropping a required scenario.
* A trajectory that only works when every adapter is the one we already have.

## What counts as evidence

* A specific event sequence beats an adjective.
* An existing artifact beats an assertion about one.
* A model experiment proves **the model only**. It is never product verification,
  never protocol verification, never "the design works".
* This repository's current code is a migration constraint and evidence about the
  problem space. It is not the answer and not the baseline a candidate must keep.
* Anything marked "unverified" in the inputs stays marked unverified in outputs.

## Honest outcomes

* Two candidates that cannot be simply ranked may both stay; say so, and say what
  observation would rank them.
* "I could not break it" and "it is correct" are different claims. Use the first.
* A clean round is a real result only if the attack dimension was actually taken
  up. Record which dimension was used, always.

|---|---|

| D05-fallback-unknown | unregistered view, unknown content type, partial data, malformed payload |

| D07-extension-burden | count what a *new module author* must learn; boilerplate, implicit coupling, ordering assumptions |
| D08-reduction | delete one core mechanism and show a required scenario still passes; or show every candidate has one mechanism too many |

# Agent Desktop：设计循环目标与场景草案

状态：目标已获用户认可；下列场景与循环参数由 I 提议，待用户查看。
未启动循环、未安装外部框架、未任命新执行者。产品代码只读。

## 用户确认的方向

独立于特定后端、面向 Agent 使用的可扩展 Desktop。对话、工具调用、模型
配置均可以成为能力，但不预设为整个产品的组织中心。
Ordessa 后端可以提供最完整能力，不是所有接入的必需前提。
不预先把 Agent、会话、任务或插件宿主指定为核心答案。
通过场景、反例与删减实验寻找宿主最小机制与扩展领域能力的边界。

## I 提议的场景集

每个场景只规定用户结果，不提前规定内部对象或必须采用哪个 UI。

| ID | 场景 | 需要设计回答的问题 |
| --- | --- | --- |
| S01 | 接入简单 Agent，仅支持文本往返 | 没有 Profile、工作区、工具和恢复能力时能否使用？ |
| S02 | 通过 Ordessa 后端使用 Pi，观察工具与授权并持续交流 | 现有真实链如何映射，哪些能力由扩展承担？ |

不要求任意第三方不可信代码热加载，不要求兼容所有协议或无限未来能力。

## 评判方式

先满足明确场景与不变式，再比较复杂度；不以文件少或自评分高判胜。
对每个候选列：核心概念、接口操作、状态权威、生命周期、扩展依赖、接入成本、
实现成本和不能覆盖的范围。不能用 execute(any)、万能 context/事件总线
隐藏接口与错误语义后宣布核心最小。

每个核心概念必须给一个“删掉它会失败”的具体场景；若移入扩展仍能满足
全部必需条件，就列作可移除候选。总复杂度包含核心、适配器与扩展作者负担。
允许保留多个不可简单排序的候选，不强行宣称存在唯一最简模型。

## 建议循环（未启动）

1. 首轮至少提出两个结构不同的候选，不以旧 mcode 方案为唯一出发点。
2. 设计者给类型/伪代码、所有权与逐步场景轨迹。
3. 攻击者给具体事件序列、被违反的不变式及最小反例；禁止只给风格意见。
4. 验证者判断成立/不成立/证据不足，必要时在隔离设计目录写小型模型测试。
   模型测试只能证明所建模型，不得冒充实际产品集成通过。
5. 设计者修订并回放所有成立反例；不得删除场景、偷偷降低要求或压制攻击。
6. 做删减攻击与新场景攻击，保存最佳候选、反例账和完整版本，不默认最后版最好。

# Best Candidate (R004 revised, A) — Namespaced resource/event core with explicit cursors, per-namespace action typing, and spawned-resource grants; envelope payload registry, invoke_id, and implicit-live-default removed as non-load-bearing.

## R4.1 Core bet
The host core is a **namespaced directory of resources**, each `(namespace_id, local_id)` plus a seq-ordered replayable event stream plus an adapter-owned open capability map. Host authority is identity, namespace isolation, subscription routing, and per-resource ordering only. "Agent", "session", "chat" are adapter-declared resource **kinds**, never host types. Capability names are adapter-chosen strings with **zero host-defined meaning and zero host behavioural authority**. Under the delete-and-show-a-failing-scenario test this round reduces further than R003: the envelope `payload_schema_id` descriptor store, the `invoke_id` correlation token, and the implicit live-only subscribe default are removed; no required scenario fails without them, and the surviving set is the minimal core that satisfies S01–S12.

## R4.2 Core concepts and operations
**Namespace.** `namespaces.open(descriptor) → NamespaceHandle{ns_id}`; `namespace.teardown(reason)`. `ns_id` host-minted per connect, never service-supplied; reconnect yields a new `ns_id`. Teardown disposes its resources and force-closes every handle subscribed to them. `resource_id = (ns_id, local_id)`; raw-id collision structurally impossible.

**Resource.** `namespace.announce({local_id, kind:string, capabilities:CapMap})` (adapter-origin, host verifies in-namespace uniqueness); `namespace.retire(local_id, reason)`; `directory.list(ns_id, filter{kind?})`; `directory.lookup(ns_id, local_id) → descriptor | ExplicitAbsent`. Content authority = producing adapter; identity/lifecycle = host.

**Event stream.** `subscribe(resource_id, from_cursor:int) → Subscription{close(), onNext(Envelope)}`. **`from_cursor` is mandatory (R004, FE-CE-011):** `from_cursor=cursor.resolve(resource_id)` begins live; `from_cursor=0` replays from first envelope in order. `Envelope{resource_id, seq:int, ts, kind:string, payload_schema_id:string, payload:opaque}`. **`payload_schema_id` is an opaque routing/selection label (R004, FE-CE-008): the host neither registers, gates, nor interprets it — it forwards every envelope.** `seq` host-assigned monotonic per resource. `cursor.resolve(resource_id) → current_seq`. Release: `Subscription.close()`, handle-scope destruction, or namespace teardown.

**Open capability map.** `capabilities.get(resource_id) → CapMap{name→{supported|not_supported|unknown}}`. Host defines no valid names, assigns no behavioural authority, never branches on a CapMap value in routing/replay/lifecycle. Absence of a name = "unknown", never "unsupported".

**ns-scoped action-type declaration (replaces the payload registry).** Action shapes are declared **at registration inside the adapter's own namespace**: `action.register(kind, action_type, params_type:ActionSchema, result_type:ActionSchema)`, keyed by `(ns_id, kind, action_type)`. No `execute(any)`: params/results are concrete declared schemas. Two namespaces using the same `kind`/`action_type`/type name never share a mutable key because the registry is per-namespace (this is the surviving FE-CE-006 isolation — now structural via namespace-local registration, not a gate on a shared payload map).

**Typed action.** `action.invoke(resource_id, action_type, params:ActionSchema) → Result | CapabilityAbsent(action_type) | OutcomeUnknown`. **`OutcomeUnknown` carries no token (R004, FE-CE-010):** the host applies the fixed invariant *an invoke whose outcome is unknown is never auto-resubmitted*; the caller correlates by the synchronous return and decides a fresh re-invoke; adapters that want idempotent auto-retry implement it themselves. `CapabilityAbsent` is returned only when the action is not registered for the resource's kind.

**Result.spawned_resource_id (spawned-resource grant; kept).** `result_type` MAY declare optional `spawned_resource_id:(ns_id, local_id)`. When populated, the host adds it to the invoking handle's accessible set. `SubscriberScope{primary_id:(ns_id,local_id), spawned:set<(ns_id,local_id)>, subscriptionHandle, typedInvoker}`; accessible = `{primary}∪spawned`. Host rejects a spawned id whose `ns_id ≠ primary.ns`. This is not sibling enumeration, not `directory.list`, not cross-namespace access. Retained against the FE-CE-009 same-ns reduction (see §R4.8): the set bounds subscription to host-observed Result ids — the provenance bound that FE-CE-004/005/007 closure rests on.

**Resource-scoped handle.** `handle_for(ns_id, local_id) → SubscriberScope{primary, spawned:∅, ...}`; mints exactly one primary; exposes no `parent`/`sibling`/`enumerateNamespace`/`directory.list`-on-namespace; `directory`/`subscribe`/`invoke` are scope-checked against `{primary}∪spawned`.

## R4.3 Boundary rules
A service adapter: (1) `namespaces.open`; (2) `announce/retire` kind + open CapMap; (3) seq-ordered pump (host assigns seq); (4) `action.register(kind, action_type, params, result)` under its own namespace; (5) explicit `not_supported` CapMap entries for absent features. "No cancel" = `CapMap{"cancel":not_supported}` (informational) AND omit `"cancel"` from the kind's action registry (structural) → `invoke(...,"cancel") → CapabilityAbsent`. `ExplicitAbsent`, `CapabilityAbsent`, `ScopeDenied`, `NamespaceGone`, `OutcomeUnknown` are distinct non-null terminals; absence never inferred from null/timeout. The adapter sees only its own namespace; no adapter-side API names or resolves another namespace's resource.

## R4.4 Extension mechanism
An extension registers a view resolver `{match: kind + payload_schema_id string, component, optional typed action bindings}`; selection exact/most-specific-first; **default fallback** = host-builtin generic view rendering resource kind, registered action names + typed param schemas, CapMap name→state pairs, the last envelope's `payload_schema_id` label (not its content), and *"No dedicated view installed; structured data available via subscription."* Unknown content is never blank and never given a run/agent reading; an unregistered `payload_schema_id` lands in the same fallback (§R4.2). A view receives only host-minted `SubscriberScope` handles. **Pair gesture:** user points at two on-screen resources; host mints `h_A=handle_for(ns_A,a)` and `h_B=handle_for(ns_B,b)` with `from_cursor=cursor.resolve(id)` (explicit live, §R4.2) and hands both over. Core records **nothing** about the pairing. View may render, subscribe via each handle's `{primary}∪spawned`, and invoke registered actions on `{primary}∪spawned`; it may **not** enumerate namespaces, derive a foreign id from a handle, register free-form event names, or hold a global context. Guarantees: resolver absent → generic view; throws → error boundary keeps delivering on still-mounted handles; unmounted mid-operation → host force-closes that view's handles incl. spawned; re-subscription uses explicit `from_cursor=cursor.resolve(id)`.

# Best Candidate (R006 revised, A) — Namespaced resource/event core with same-namespace scoped handles; spawned-set reduced to provenance-free ns_id check; S09 confirmed as core+adaptation joint.

## R6.1 Core bet

The host core is a **namespaced directory** of `(ns_id, local_id)` resources, each with a seq-ordered replayable event stream and an adapter-owned open capability map, plus per-namespace typed actions. Handles are **namespace-scoped subscription tokens** — a handle can subscribe to and invoke any resource within its own namespace, and nothing outside it. This round reduces the R004 candidate further: the per-handle `spawned` set is eliminated, replaced by a same-namespace subscription rule that passes every required scenario including S08 without accumulating per-handle state (proven by the Model2 experiment below), and S09 is confirmed covered as a core+adaptation joint trajectory.

## R6.2 Core concepts and operations

**Namespace.** `namespaces.open(descriptor) → NamespaceHandle{ns_id}`; `namespace.teardown(reason)`. `ns_id` host-minted per connect, never service-supplied; reconnect yields a new `ns_id`. Teardown disposes its resources and force-closes every handle scoped to that namespace. `resource_id = (ns_id, local_id)`; raw-id collision structurally impossible.

**Resource.** `namespace.announce({local_id, kind:string, capabilities:CapMap})` (adapter-origin, host verifies in-namespace uniqueness); `namespace.retire(local_id, reason)`; `handle.directory_list({kind?}) → [resource_descriptor]`; `handle.directory_lookup(local_id) → descriptor | ExplicitAbsent`. Content authority = producing adapter; identity/lifecycle = host.

**Event stream.** `handle.subscribe(resource_id, from_cursor:int) → Subscription{close(), onNext(Envelope)}`. **`from_cursor` is mandatory (FE-CE-011):** `from_cursor=cursor.resolve(resource_id)` begins live; `from_cursor=0` replays from first envelope. `Envelope{resource_id, seq:int, ts, kind:string, payload_schema_id:string, payload:opaque}`. **`payload_schema_id` is an opaque routing/selection label (FE-CE-008): the host neither registers, gates, nor interprets it.** `seq` host-assigned monotonic per resource. `cursor.resolve(resource_id) → current_seq`. Release: `Subscription.close()`, handle-scope destruction, or namespace teardown.

**Open capability map.** `capabilities.get(resource_id) → CapMap{name→{supported|not_supported|unknown}}`. Host defines no valid names, assigns no behavioural authority, never branches on a CapMap value. Absence of a name = "unknown", never "unsupported".

**ns-scoped action-type declaration.** `action.register(kind, action_type, params_type:ActionSchema, result_type:ActionSchema)`, keyed by `(ns_id, kind, action_type)`. No `execute(any)`: params/results are concrete declared schemas.

**Typed action.** `handle.invoke(resource_id, action_type, params:ActionSchema) → Result | CapabilityAbsent(action_type) | OutcomeUnknown`. **`OutcomeUnknown` carries no token (FE-CE-010):** fixed invariant — an invoke whose outcome is unknown is never auto-resubmitted; caller correlates by synchronous return. `CapabilityAbsent` returned when action is not registered for the resource's kind. `Result` is a typed schema; `spawned_resource_id:(ns_id,local_id)` MAY be a field in the result schema (informational — the host does not use it for access control).

**Namespace-scoped handle.** `handle_for(ns_id) → SubscriberScope{ns_id, subscriptionHandle, typedInvoker, directory_list, directory_lookup}`. **The permission rule is: a handle may subscribe to or invoke any resource where `resource_id.ns_id == handle.ns_id`.** The handle exposes no `parent`/`sibling`/`enumerateForeignNs`; cross-namespace access is structurally impossible because the handle carries exactly one `ns_id`. A view receives only host-minted SubscriberScope handles. `directory.list` and `directory.lookup` are handle-scoped (within the handle's own namespace). **No per-handle spawned/accessible set is maintained.**

## R6.3 Boundary rules

A service adapter: (1) `namespaces.open`; (2) `announce/retire` kind + open CapMap; (3) seq-ordered pump (host assigns seq); (4) `action.register(kind, action_type, params, result)` under its own namespace; (5) explicit `not_supported` CapMap entries for absent features; (6) on reconnect, deduplicate/reorder by `(ns_id, resource_local_id, seq)` before presenting to the stream. "No cancel" = `CapMap{"cancel":not_supported}` (informational) AND omit `"cancel"` from the kind's action registry (structural) → `invoke(…,"cancel") → CapabilityAbsent`. `ExplicitAbsent`, `CapabilityAbsent`, `ScopeDenied`, `NamespaceGone`, `OutcomeUnknown` are distinct non-null terminals. The adapter sees only its own namespace. No adapter-side API names or resolves another namespace's resource.

## R6.4 Extension mechanism

An extension registers a view resolver `{match: kind + payload_schema_id string, component, optional typed action bindings}`; selection exact/most-specific-first; **default fallback** = host-builtin generic view rendering resource kind, registered action names + typed param schemas, CapMap name→state pairs, the last envelope's `payload_schema_id` label (not its content), and *"No dedicated view installed; structured data available via subscription."* Unknown content is never blank and never given a run/agent reading. A view receives only host-minted `SubscriberScope` handles. **Pair gesture:** user points at two on-screen resources; host mints `h_A=handle_for(ns_A)` and `h_B=handle_for(ns_B)` with explicit `from_cursor=cursor.resolve(id)` for initial subscription; hands both over. Core records **nothing** about the pairing. View may render, `directory_list`/`subscribe`/`invoke` within its handle's namespace; it may **not** enumerate other namespaces, derive a foreign ns_id from a handle, register free-form event names, or hold a global context. Guarantees: resolver absent → generic view; throws → error boundary keeps delivering on still-mounted handles; unmounted mid-operation → host force-closes that view's handles; re-subscription uses explicit `from_cursor`.

## FE-CE-012: Host dedup key (ns,resource,seq) is vacuous — no component can deduplicate as specified

### 1. Exact event sequence

1. Adapter pumps event A into resource (ns_A, "log"). Host assigns seq=1. Subscriber receives Envelope{resource_id=(ns_A,"log"), seq=1, payload=content_A}.
2. Adapter pumps event B into same resource. Host assigns seq=2. Subscriber receives Envelope{seq=2, payload=content_B}.
3. Link drops mid-stream; TCP reconnects without triggering `namespace.teardown` (the connection is the same ns_id — "reconnect yields a new ns_id" applies to a *full* reconnect, not a transient drop within the session). ns_A is still alive.
4. Adapter, uncertain whether A and B were delivered, replays A and B into its pump function targeting resource (ns_A, "log").
5. Host receives them, assigns seq=3 and seq=4 (monotonic per resource — the host has no reason to reuse 1,2; it always increments).
6. Subscriber receives: Envelope{seq=3, payload=content_A}, Envelope{seq=4, payload=content_B}.
7. Host's "dedup by (ns,resource,seq)" checks whether (ns_A,"log",3) or (ns_A,"log",4) have been seen before → they haven't → both pass.

### 2. Invariant broken

"host dedups/reorders by `(ns,resource,seq)`" (R6.5-S09 step 2) and "seq host-assigned monotonic per resource" (R6.2 Event stream paragraph: "`seq` host-assigned monotonic per resource"). The dedup key requires two envelopes to collide in (ns,resource,seq), but monotonic-per-resource host assignment guarantees every envelope for a given resource has a unique seq. The dedup predicate is `false` for all inputs.

### 3. Minimal version

Remove step 3 (the link drop motivation). The counterexample stands simply: the adapter pumps the same content twice for any reason (bug, retry, race). Host assigns fresh seq to each arrival. Dedup by (ns,resource,seq) can never fire. The mechanism is structurally vacuous regardless of network events.

### 4. User-visible consequence

S09: the user sees duplicate progress events or repeated tool-call notifications in the log view. The design's S09 scenario requires "who confirms facts, restores state, and prevents double execution." The host claims dedup but provides none. The adapter is instructed (R6.3 item 7) to dedup by (ns,resource,seq) — a key it cannot compute (see FE-CE-013) — so it cannot implement this either. The user sees duplicates unless the adapter happens to implement idempotency via its own protocol-level keys, a mechanism the design neither specifies nor requires as a core guarantee.

## FE-CE-013: Adapter boundary rule 7 instructs dedup by host-assigned seq — the adapter has no access to it at pump time

### 1. Exact event sequence

1. Adapter opens connection → host mints ns_A. Adapter announces resource (ns_A, "log").
2. Adapter pumps event A. Host assigns seq=1 internally and delivers Envelope{seq=1} to subscribers. The design's pump interface is not a return-value-with-seq contract — R6.2 defines the host's seq as "host-assigned monotonic per resource" with no mention of the pump function returning the assigned seq to the caller. The adapter's `pump(event)` call completes without learning seq=1.
3. Link drops. Adapter decides to re-pump A as part of its "reconnect dedup/reorder by (ns_id, resource_local_id, seq)" (R6.3 item 7).
4. The adapter needs to know: "has (ns_A, log, seq=1) already been pumped?" — but it never learned that its event got seq=1. The dedup key in the boundary rule is not in the adapter's epistemic state.
5. Adapter re-pumps A. Host assigns seq=2. Duplicate delivered.

### 2. Invariant broken

Boundary rule R6.3 item 7: "on reconnect, deduplicate/reorder by (ns_id, resource_local_id, seq) before presenting to the stream." Simultaneously, R6.2: "`seq` host-assigned monotonic per resource." The adapter cannot deduplicate by a field assigned by the host that the adapter does not observe. The boundary rule is either (a) a typo for the adapter's own protocol id (which would mean the stated key is wrong), or (b) an unimplementable instruction, making item 7 a core-internal leak — the adapter must know a host-assigned seq value to comply.

### 3. Minimal version

Steps 2 and 4 alone: adapter pumps once (receives no seq back), adapter needs to dedup by seq. No network event needed. The instruction is impossible given the design's stated ownership of seq.

### 4. User-visible consequence

The adapter author either (a) ignores item 7 because it's unimplementable (host-assigned seq is not in their hands), in which case S09 duplicates reach the user; or (b) the pump function actually DOES return the host-assigned seq (not in the interface spec), in which case the adapter must maintain a per-resource set of delivered seq values — unbounded growth within a long connection, contradicting R6.8's claim that "D11 growth is addressed... removing the spawned set eliminates the per-handle accumulated-state growth concern entirely." The growth concern simply relocated from host handle to adapter pump state.

## FE-CE-014: Host "reorder" is identity — S09's out-of-order premise has no core correction mechanism

### 1. Exact event sequence

1. Remote system emits logical events in order [A, B] where A→B is a dependency (e.g., "create_session" → "tool_result"). Network delivers them reversed: B arrives first, A second.
2. Adapter's pump (boundary rule 3 says "seq-ordered pump" — meaning the adapter pumps in arrival order) pumps B, then A.
3. Host assigns seq=1 to B, seq=2 to A (arrival order = host order).
4. Subscriber receives: Envelope{seq=1, content=B}, Envelope{seq=2, content=A}. Logical order is inverted.
5. S09 claims "host dedups/**reorders** by (ns,resource,seq)." Reordering by host-assigned seq is identity — the host assigned seq in that order. The "reorder" operation has zero effect.
6. The view renders "tool_result" before "create_session." User sees nonsensical interleaving.

### 2. Invariant broken

R6.5-S09 step 2: "host dedups/reorders by (ns,resource,seq)." If host-assigned seq defines the order, sorting by it is a no-op. The design claims a reordering mechanism that structurally cannot correct any order. S09's premise — "events arrive duplicated and **out of order**" — requires either a remote-stable seq (in the envelope, adapter-assigned) or a reorder buffer with timeout. The Envelope type `{resource_id, seq, ts, kind, payload_schema_id, payload:opaque}` has ts, but "reorders by seq" not "reorders by ts." The host has no mechanism to use ts for reordering.

### 3. Minimal version

Steps 2-3-4-5: pump B then A, host assigns 1 then 2, subscriber sees B before A. "Reorder by seq" is identity. Remove any reconnect/dedup framing — this is pure order corruption within one stable namespace.

### 4. User-visible consequence

The S09 scenario requires the host to handle out-of-order events. The design's only claimed mechanism (reorder by host-assigned seq) is a no-op. If boundary rule 3 ("seq-ordered pump") pushes order correction entirely onto the adapter, then the host has no D01 mechanism at all, and S09's "host dedups/reorders" claim is a capability lie (the host does neither in any non-identity way).

```python
"""Model: host dedup by (ns,resource,seq) with seq=host-assigned monotonic.
Proves: the dedup predicate never fires for replayed content.
Only proves the model, not the design."""

class Host:
    def __init__(self):
        self._next_seq = {}  # resource_id -> next seq
        self._seen = set()   # (ns,local_id,seq) tuples delivered

    def assign_seq(self, resource_id):
        s = self._next_seq.get(resource_id, 0)
        self._next_seq[resource_id] = s + 1
        return s

    def deliver(self, resource_id, seq):
        key = (resource_id[0], resource_id[1], seq)
        if key in self._seen:
            return False  # dedup fired
        self._seen.add(key)
        return True  # delivered

def pump_event(host, resource_id, content):
    seq = host.assign_seq(resource_id)
    return (seq, host.deliver(resource_id, seq), content)

def run():
    h = Host()
    res = ("ns_A", "log")
    # Normal: adapter pumps A, B
    s1, delivered1, c1 = pump_event(h, res, "event-A")
    s2, delivered2, c2 = pump_event(h, res, "event-B")
    assert s1 == 0 and s2 == 1
    assert delivered1 and delivered2

    # Reconnect: adapter replays A, B
    s3, delivered3, c3 = pump_event(h, res, "event-A")
    s4, delivered4, c4 = pump_event(h, res, "event-B")
    assert s3 == 2 and s4 == 3  # new seq, never seen before
    print(f"Replayed A: seq={s3} delivered={delivered3} (dedup fired: {not delivered3})")
    print(f"Replayed B: seq={s4} delivered={delivered4} (dedup fired: {not delivered4})")
    assert delivered3, "DEDUP FAILED TO FIRE: replayed A delivered as new"
    assert delivered4, "DEDUP FAILED TO FIRE: replayed B delivered as new"
    print("MODEL VERDICT: host dedup by (ns,resource,seq) never fires.")
    print("Monotonic host-assigned seq guarantees no key collision.")
    return True

run()
```

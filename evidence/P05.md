## 旧 pending 发送优先恢复返修（2026-09-14）

代码提交：`b6d0bc6f`。问题：已经产生 `requestId` 的旧发送在上一阶段的顺序下可能被"当前草稿"的问题挡住——
配置 rejected/unavailable、Profile/Workspace 暂时缺失、附件未 stage、文本已改变，都会让提交在查询旧请求
**之前**就返回，于是旧请求既没被结算、也没有建立新发送。

**顺序（现在的语义）**

1. `resolvePendingAgentBoxSend(client, scopeKey)`（`application/session/wire-send.ts`）读取该 scope 的
   旧 pending；没有则返回 null 且**不触碰 transport**；有则以**原 `requestId`** 调
   `sendOutcome.query({requestId})`，不需要 message/profile/workspace/overrides。
2. `submitAgentBoxComposer`（`application/session/agentbox-composer.ts`）先校验 `draftVersion` 可作为
   intentKey，随后立即尝试恢复：拿到 decision 就**只**返回它，不再检查当前消息、附件、Profile、Workspace
   或配置；`acceptedForDraft` 仍按"旧 intentKey === 当前 draftVersion"计算，所以旧请求 accepted 而草稿已
   更新时不清新草稿，`unknown` 保留同一 requestId，`rejected_before_accept` 清旧 pending 但保留草稿。
3. 只有返回 null（scope 干净）才执行：当前草稿/附件校验 → 身份校验 → `config.resolve` → resolved 后发送。
4. `sendAgentBoxMessage` 内部仍调用同一个恢复函数（单一 `sendOutcome.query` 状态机），因此两个并发提交
   即使都在前置检查时看到"无 pending"，也只有一个能创建身份。

**生产能力门**（`app/composition/wiring/agentbox-main-chat.ts`）区分两种动作：有 pending 时
`sendAvailable` 只要求「服务可调用 + hello 声明 `sendOutcome.query` + 有 draftScopeKey」，不要求
`config.resolve`、不要求 `sessions.createAndSend`/`sessions.send`、也不要求当前 Workspace/Profile 仍可解析，
`onSubmit` 不再因 `!workspace` 提前返回（恢复路径传 `profileId: null`/`workspaceId: null`）；scope 干净时
保持上一阶段的门（`config.resolve` + 该路由的发送动词 + 当前服务身份）。仅当 pending 存在却又缺
`sendOutcome.query` 时 `sendAvailable=false`——**有未结算请求时不允许建立新发送**，这正是不变量 6 的顺序
要求在门上的体现。

**这与"新发送的配置校验"不冲突**：`config.resolve` 只在"没有旧 pending、准备建立新发送意图"时执行；
scope 清空后的新发送仍严格 `config.resolve → createAndSend/send`，rejected 与 typed error 仍不发送
（回归用例保留并通过）。

**行为测试（6 files / 62 tests passed，exit 0）**：pending 优先于配置（`config.resolve` 被调用即抛错，
实际调用序列严格等于 `['sendOutcome.query']`）；pending 优先于当前草稿校验（附件 unstaged + profileId/
workspaceId 为 null + 文本不同，仍只查询）；旧 accepted + 新 draftVersion → `acceptedForDraft=false`；
unknown 保留同一 requestId 且第二次仍只查同一 id（不产生新 requestId）；rejected 清 pending、返回旧
rejection、当前草稿不发送；能力门三种情形（有 pending 只声明 query → 可提交，同一 hello 无 pending →
不可提交，有 pending 缺 query → 不可提交）；回归：无 pending 仍 `config.resolve → createAndSend/send`、
rejected 不发送、typed resolve error 不发送。`resolvePendingAgentBoxSend` 另有无 pending 零调用与
按原 requestId 结算两个用例。

`npm run typecheck` 三项目通过；改动 6 个 TS/TSX 文件 ESLint 0 error / 0 warning；`git diff --check` 干净。

**身份匹配返修（代码检查点 `072c7eac`）**：此前 `AgentBoxWorkspaceSelection.wsl` 只有
`{distribution, rootPath}`，`selectionForTarget` 因此丢弃了 target 的 user，匹配只比 kind/host/path；local
也只比 kind/path，未要求 host/user 为 null。这会把同一 distro/path 下另一用户的记录当成当前 Workspace，
跳过应当发生的 `workspaces.open` 并采用错误的服务 Workspace ID。现在：

- 中立 selection 的 WSL 分支携带 `user`，取值与 open payload 同源的已验证身份（生产为
  `selectedWsl.actualUser`）；
- 匹配要求完整三元组 + normalized path 全等（local 必须 `{local, null, null}`）；
- 唯一的例外仍是显式 `serviceWorkspaceId` 直查（Session 自己的 workspaceId 权威），语义未变。

只有错 user 的记录（含 user 未知的记录）返回 null、带 host 或 user 的 local 记录永不复用、wiring 层在缓存
只有 bob 时不得采用 bob、必须 open 一次且 payload user 精确为 alice、服务返回前保持 provisional 草稿作用域

   后端不可用时的常态）仍然全屏遮罩，把可用壳挡死。改为：只有**确认“确实需要引导”**

## C 段 Profile 默认配置编辑（2026-09-14，串行 CAS 保存）

Profiles 页的 `config.describe` 从只读投影变为**可编辑的 Profile 默认配置**，接到 wire-v1 已锁定的
`profiles.updateConfig(requestId, profileId, expectedVersion, values)`。该方法**替换整份** Profile
配置，因此客户端从未把它当成局部 patch：保存时提交的 `values` 是「服务当前描述 + 用户显式编辑」
的完整集合。

### 能力门与控件来源

- `ProfileMaintenancePort.updateConfig` 由可选改为**必选**；生产组合的能力门同时要求
  `profiles.create`、`profiles.update`、`profiles.updateConfig`、`profiles.archive`。缺任一方法时
  `activeMaintenance` 为 undefined：页面只显示准确不可用说明与只读 `config.describe` 摘要，
  不渲染任何会假装保存的控件（新增反例：hello 声明 create/update/archive 而无 updateConfig 时，
  无 Save、无名称输入、无编辑器）。
- 编辑控件全部由服务描述渲染：`enum`→Select、`string`→Input（`multiline=true` 时用既有
  Textarea）、`boolean`→Switch、`model_slot`→目录 Select；未知 kind 渲染为空，不自造字段。
  控件标签沿用服务给的 `controlId`（数据呈现，与 composer 临时配置一致），不硬编码品牌名。

### 模型引用语义

- 选项来自 `$agentBoxProviderModels`，按 `ProviderModel.harness` 与 `Profile.harness` 的
  **不透明等值**过滤（同一目录下另一 harness 的模型不出现在选项里）。
- 只发送 `{providerId, modelId}`；含 `/` 的 id 原样保留，不 split、不拼接、不做品牌解析。
- `availability=unavailable` 的项按服务原因标注并禁选（组件自身拒绝，即使点击到达处理器也不写入）；
  `availability=unknown` 可选但标注「未验证」，不呈现为已验证。
- 当前 descriptor 引用若已不在目录，仍按服务原值显示并可选「恢复默认」；多模型槽位由多个服务
  `model_slot` control 各自独立编辑（不按 Harness 名硬编码字段）。

### 整份保存与串行 CAS

- `buildProfileConfigValues` 是纯函数：未编辑与 `securityLockedIds` / `editable=false` 的控件按服务
  当前值原样带回（锁定控件既不编辑也不提供「恢复默认」，删除其值同样等于改变它）；用户显式恢复
  默认的控件**从 values 省略**，不用推测的默认值顶替；服务未声明值的控件同样省略。
- 名称与配置同时变化时严格串行：先 `profiles.update`（当前 version）→ 只采纳其返回 Profile →
  以该返回的新 version 作为 `updateConfig` 的 `expectedVersion` → 只采纳 `updateConfig` 返回的
  Profile → 成功后重新读取 `config.describe` 并采用服务规范化结果。
- 部分成功：改名成功而配置失败时，store 保留服务确认的新名称与新 version，配置草稿保留且错误可见；
  重试只用新 version 重发配置，不再重发已经成功的改名。
- `CONFLICT_VERSION` 等 typed error 不使用本地草稿覆盖服务投影；请求未决期间重复点击只发送一次；
  用户切换 Profile 后迟到 descriptor 不重绘到新 Profile；成功后只显示服务返回的 Profile/descriptor，
  不显示乐观伪造记录；`effectiveFor` 如实呈现为 next send（`data-effective-for`），不声称影响运行中的
  Execution。

## 三类边界

1. 会话核心：会话导航、发送、通用文本/思考/工具/授权/执行状态与流事件投影。
   核心可知道通用能力与不支持状态，不知道 Pi/Hermes 配置文件、启动命令和秘密。
2. 服务适配模块：声明身份/能力，将连接、会话列表、创建/发送、订阅、历史、停止/
   授权等已有服务协议映射到中立接口；可选操作缺席要显式表示。
   不要求后端为了前端抽象而更换 wire；既有 AgentBox wire 放在适配层。
   Pi 若由 Ordessa Server 管理，作为该适配器发现的 Harness 实例，不能为了
   “Pi 插件”重复造一套传输。GUI 注册不能凭空让服务端支持一个新 Harness。
3. UI 扩展：按需提供导航/设置页、会话头/输入区附件控件、工具详情渲染、侧面板
   等类型化插槽。服务无定制 UI 时使用通用默认值，不强制注册全部组件。
   核心保留消息顺序、关联 ID 和状态一致性，不能把这些交给互不协调的小组件。

复用现有注册框架，先做编译期内置模块。不要新增远程任意代码加载或插件市场。
注册有命名空间、冲突报错、明确替换优先级、销毁/取消订阅、渲染错误隔离。
同进程 React 扩展的错误边界不等于不可信代码安全沙箱，不作此宣称。
服务切换要隔离 session 状态/订阅，旧流不能落入新服务的会话。
业务模块经窄 host API 访问能力，避免给整个全局 store/裸凭据作为“通用上下文”。

## 可执行验收

- 一个现有真实服务适配模块（优先 Ordessa Server/Pi 所在链）经过核心运行；
  没有活服务时记录未验证，不改后端填坑。
- 第二个确定性的测试服务模块，通过独立注册提供不同的能力组合、两轮消息、
  工具事件/授权样例。它明确是 mock，只验证前端可扩展性。
- 用固定核心版本展示“新增测试模块 + 注册/自动发现”即可接入；列出新增服务
  改动文件，验证不需在核心加服务名分支。这是边界证据，不是第二种真实 Harness。
- 覆盖服务切换/卸载后的订阅清理、可选能力缺席、未知工具的通用回退、
  插槽渲染异常隔离；现有会话呈现关键回归不退化。
- 跑对应类型检查与测试、实际 UI 展示；无法 GUI 操作则写可复现用户试用步骤，
  不把测试适配器数据当真实 Pi 回复。
- 没有因本任务增加后端源码改动、修改 publishing main 或 push。

### 2.1 交回的缺口（不自行补）

**实测**：WSL 路径上 `additions`/`deletions` **恒 null**，而 `reason` 也是 null。
原因是 `handlers.py:1042` 起的 `wsl` 分支只做 `parse_porcelain_v2`（branch/changed/ahead/behind），
没有 `local` 分支那一步 `diff --numstat HEAD`；`connector.py:141` 的 `read_only_git_status`
也只发一条 status 命令。

这**不是** 62 契约的字面违反：62 的 `reason` 是**答案级**一个字段（报告 §规则表：非仓库/无 git ⇒ 全 null +
`GIT_NOT_A_REPOSITORY`；本机路径也有"无提交 ⇒ 增删行 null"而不带 reason 的情形），并没有"字段级 reason"这个概念。
但 083 的 G1 写的是"六字段（或各自的 `reason`）"，按这句读法 WSL 腿只做到"六字段俱在、其中两个结构上永不为真"。
于是卡面上一个 WSL 工作区的增删行永远是空格且无解释。两种补法语义不同——WSL 侧补一次 numstat（多一条命令、
多一次超时面），或接受"WSL 不报增删行"并把它写进 62 的契约文字。这是产品/契约决定，
**记录并交回调度者**，本单不改 wire、不改实现。

### 3.1 为什么不能取样真飞行中的 WSL 执行（第一手阻塞）

1. **实测**（读码 + 跑）`runtime.py:140` 的 `_builtin_connector`：
   `if os.name != "nt" or not manifest or not worker: return None` —— 即使把
   `AGENT_BOX_WSL_WORKER_MANIFEST`/`AGENT_BOX_WSL_WORKER_LINUX_PATH` 都设上，Linux/WSL 侧也不组合连接器。
2. **实测** `build_runtime_from_sidecar_deployment` 的签名（`runtime.py:449`）：只收
   `data_root/deployment_path/secret_store/plugin_root/mount_bindings`，**没有 `connector=`**，
   所以走部署文档的那条真执行路径无法从本侧注入连接器。
   （能注入连接器的 `build_runtime(..., connector=…)` 不读 sidecar 部署文档，两者不是同一条组合路径。）
3. **实测** `scripts/server-round1/env-provider-gate.py --placement` 只接受 `local|ssh`；本单 `write_paths`
   不含 `scripts/**`，不能加 `wsl` 这一档。
4. 通道本身是活的（**实测**）：用真 c11 manifest 构造 `WslConnector` 后 `probe()` 完成真握手 ——
   `probe_id=probe-ff672e9f45ce46d297007b3561ada361`、`worker_version=0.1.0`、
   `worker_digest=sha256:c1e353c89609ab2feed0765205feeb3eb4c8db9679f353ba4065302df35a2457`。
   阻塞在**组合**，不在通道。
5. 这条链路上另有一个真缺陷已被用户拍给新单：**已投递 090 `placement-routing`**（`b7ca376`，裁决 R-0012）——
   Windows 宿主 + WSL 工作区的一轮没有路由到 WSL worker，而是回退 `sandbox-windows` →
   `SANDBOX_PROVIDER_UNRESOLVED` → `DispatchAmbiguous`。真飞行中的 WSL 执行取样归 090 的门更合适
   （它有 `src/**` 写权），本单不越界。

**精确剩余**：在 090 之后（或在 Windows 侧、`build_runtime_from_sidecar_deployment` 能组合 WSL 连接器的形态下）
补一次"真 Worker 飞行中"的 `executions.list` 取样。

# P12 — 订阅/账号管理（官方登录、多账号、状态可见）

基线：P11 之后（串行）。配对后端单：**56**（订阅凭据类别、登录态与探测）。
参照：`farion1231/cc-switch` 的"Official Login 预设 + 切过去跑 logout/login + Codex 多官方账号"
（取证口径与"学/不学"见 P11 的补节）。

```text
之前
└── 凭据：只有 api-key 一种，且只被"供应商记录"引用
之后
├── 账号列表        ◀ 订阅（官方登录）/ API key 两类并列；显示 归属家族、账号标识、状态、最后验证时间
├── 绑定            ◀ 一个 profile 绑一个账号（**多账号 = 多 profile**，不做同一 profile 热切换）
└── 手动登录引导     ◀ 用户在**执行侧**用 harness 官方流程登录；我们只引导与观测，不代填、不抓取
```

## 目标

把"订阅"做成**一等公民**：与 API key 并列的一条凭据类别，能在列表里看到、能被 profile 绑定、
**状态可观测**（有效/过期/未知），并且**登录流程由用户亲自完成**。

## 关键判断（先说清，免得做歪）

1. **订阅不是端点，是账号**：API key 描述"往哪儿发请求"，订阅描述"用谁的账号"。二者在记录里**并列**，
   都通过引用绑到 profile，**都不内联密钥**。
2. **登录态住在该 profile 的原生 home 里**（`auth.json` 一类，harness 自己写、自己刷新）——
   这正是 45 的"原生目录是事实来源"；我们**不把它搬进 SecretStore**（搬了就要替它刷新令牌，
   而且要每次执行写回，直接冲突）。
3. **多账号 = 多 profile**：一个 profile 一份 home，就一个账号。**不做**"同一 profile 热切换账号"
   （两个账号共用一份 home 必然互相污染）。列表里要**如实说明**这一点。
4. **绝不碰用户本机登录态**：登录必须**在执行侧、对我们自己的 profile home** 跑 harness 的官方登录流程；
   不读 `~/.codex` 等宿主目录、不代填账号密码、不抓取令牌、不把令牌显示或落库。
5. **扫描边界要写明**：45 的凭据扫描是**按我们注入的那次性值精确匹配**，所以它**不会**误伤订阅登录态；
   若将来有人把"home 里有令牌"当成缺陷，这条要能挡住。

## 阶段

**A 盘点与对照**：现状（`credentials.list` 的 kind、profile 的 `credentialId`、45 的 home 与扫描规则）→
新模型的三栏表；**没有数据来源的元素不实现**。

**B 列表与绑定**：账号列表（订阅 / API key 两类、归属家族、账号标识、状态、最后验证时间）；
profile 绑定改为"账号或 API key 记录"二选一；绑定关系在会话里可见（P08 的输入条会显示生效值）。

**C 登录引导**：给出"在该 profile 上登录"的引导（执行侧命令 + 何时可取消 + 完成后如何验证），
**不代填、不抓取**；失败按类型化码显示原因。

**D 状态**：状态来自后端 56 的探测（有效 / 过期 / 未知）；**未知就显示未知**，不猜、不自动重登。

**E 回归与收口**：既有设置/凭据用例不退化；补"登录态不被显示""未授权路径不出现"的反例；更新
status/evidence；释放写权。

## 门

| 门 | 断言 |
| --- | --- |
| **G1 两类并列** | 订阅与 API key 在列表里是两类凭据，**都不内联密钥**，都只能被引用 |
| **G2 状态诚实** | 状态来自后端探测；未知即未知；**不得**显示"有效"当占位 |
| **G3 零泄漏** | 令牌/账号密码在任何界面、日志、证据里**零出现**；有反例用例 |
| **G4 不越界** | 不读宿主原生登录态、不代填、不抓取；多账号 = 多 profile 的说明**可见** |
| **G5 不退化** | 既有设置/会话用例计数不降；保护路径零改动；后端仓零写入；不碰 main、不 merge、不 push |

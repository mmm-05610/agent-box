# Product concept
>
> Historical record — describes an earlier architecture or validation state and is not current implementation guidance.

> 文档导航：[总目录](../README.md)

产品名：**PineCare 智能客服**。

PineCare 是面向虚构小型电商品牌“松果商店”的本地智能客服机器人。用户可以像使用真实在线客服一样：

- 咨询退款、配送、保修和会员政策；
- 查询模拟订单状态；
- 进行有上下文的多轮追问；
- 查看回答所依据的知识库来源；
- 在机器人无法可靠回答时创建人工支持工单；
- 刷新页面后继续查看最近对话。

它不是通用聊天机器人，也不是客服平台，而是一个完整、可运行的客服产品 vertical slice。

观众应能在 30 秒内理解：

> 这是一个会查公司政策、会查订单、不知道时会转人工，而且不会乱承诺的客服机器人。

# Target user

主要用户是松果商店的消费者，典型需求包括：

- 购买前了解配送、退换货和保修政策；
- 购买后查询订单状态；
- 判断订单是否还能取消或修改地址；
- 管理 Plus 会员订阅；
- 在 FAQ 无法覆盖时联系人工客服。

Demo 不包含真实用户账户。订单查询使用明确标注为演示数据的订单号，例如 `ORD-1001`。

# Demo business background

采用题目建议的业务方向，并将其收敛为：

> 一家销售桌面办公用品，同时提供 Plus 配送会员的小型电商“松果商店”。

这个背景适合 Demo，因为：

- 退款、发货、改地址、保修、会员等问题人人都能理解；
- 同时包含实体订单和简单订阅，但不需要行业专业知识；
- FAQ 检索、订单工具和人工升级都有自然使用场景；
- 可以使用完全本地的模拟数据；
- 不需要支付、物流或 CRM 外部集成。

产品目录本身不需要实现。Demo 只需让用户知道松果商店销售键盘、支架、收纳用品等普通办公商品。

# Core user flows

## Flow A：知识库可以直接回答

用户问：

> 退款多久到账？

系统行为：

1. 检索退款相关知识条目；
2. 找到明确政策；
3. 回答退款原路退回通常需要的时间；
4. 在回答下方显示引用，例如“退款政策 · 退款到账时间”；
5. 用户可以展开引用，查看知识库原文摘要。

成功标准：答案明确、简短，并且引用真实存在。

## Flow B：知识库只有部分相关内容

用户问：

> 我买的东西不太合适，现在应该怎么办？

该问题没有说明是否发货、是否拆封、是否超过退货期限。

系统行为：

1. 检索退货条件和退款流程；
2. 只说明知识库可以确认的通用规则；
3. 明确指出缺少的信息；
4. 追问一个最有价值的问题，例如“商品是否已经签收，以及签收距今是否超过 14 天？”；
5. 不自行假设订单状态或商品情况。

## Flow C：知识库无法回答

用户问：

> 你们明年会不会在成都开实体店？

系统行为：

- 明确表示现有知识库没有相关信息；
- 不预测、不编造；
- 提供“创建人工支持工单”操作；
- 用户确认后生成本地工单号；
- 展示工单状态卡片。

## Flow D：多轮对话

用户：

> 我的订单已经发货了。

机器人：

> 如果订单已经交给承运商，通常不能直接修改地址。你可以提供演示订单号，我可以查询具体状态。

用户：

> ORD-1001，那还能改地址吗？

系统行为：

1. 从当前对话理解“那”指该订单和修改地址；
2. 调用本地订单查询；
3. 根据实际模拟状态回答；
4. 同时引用“修改收货地址”政策；
5. 不宣称已经修改地址。

对话上下文只需覆盖当前会话中的近期消息，不需要长期用户记忆。

## Flow E：历史记录

- 新对话创建后出现在左侧最近对话列表；
- 首条用户消息生成简短标题；
- 刷新页面后仍能看到消息；
- 点击最近对话可恢复完整聊天内容；
- 至少保存最近 20 个对话，不要求搜索、归档或分页管理。

# MUST HAVE

1. 产品化 Chat UI；
2. 创建和打开 conversation；
3. 发送用户消息并展示机器人回复；
4. Conversation、message 持久化；
5. Repo 自带 FAQ/知识文档；
6. 知识检索和相关内容排序；
7. 基于检索结果生成 grounded answer；
8. 回答显示真实 source citation；
9. 无可靠答案时明确 fallback；
10. 用户可确认创建本地人工支持工单；
11. 模拟订单状态查询；
12. 当前会话内的基本多轮上下文；
13. Loading、空状态、API 错误和重试状态；
14. 后端单元、检索、行为和 API 集成测试；
15. 前端最小组件测试；
16. 一条端到端 smoke test。

MUST HAVE 不包含登录、后台管理或真实外部集成。

# SHOULD HAVE

- 根据首条消息自动生成简短会话标题；可使用确定性截断规则，不必调用 LLM；
- 三个可点击的示例问题；
- Citation 展开面板，显示来源标题和相关原文片段；
- 回答中区分“知识库政策”和“订单查询结果”；
- 工单卡片显示编号、摘要、创建时间和 `Open` 状态；
- 用户可以取消尚未确认的转人工操作；
- 桌面和常见手机宽度下均可使用；
- LLM 不可用时显示明确错误，并允许重试，不把错误伪装成客服回答；
- Demo 数据一键重置或随数据库初始化自动写入。

# NICE TO HAVE

- 对 citation 中命中的关键词进行高亮；
- 用户可复制机器人回答；
- 对机器人回答提供简单的“有帮助/没帮助”按钮，但不必持久化；
- 会话标题手动重命名；
- 支持流式显示回答；
- 用一个可见的小标签说明本次回答使用了“知识库”“订单工具”或“人工工单”；
- 本地离线的小型 embedding 模型作为可选检索增强。

这些功能只能在 MUST HAVE 全部稳定后添加。

# OUT OF SCOPE

- 用户注册、登录和权限管理；
- 多租户；
- 真实客户身份验证；
- 支付、物流、订单或会员系统集成；
- Zendesk、Intercom 或 CRM 集成；
- 生产级人工客服工作台；
- FAQ 编辑后台和复杂内容管理系统；
- 工单分配、SLA、客服排班和工单流转；
- 多渠道客服；
- 多语言；
- 语音、图片和文件上传；
- 商品推荐和购物车；
- 真实退款、取消、改地址等写操作；
- 分布式微服务；
- 独立向量数据库；
- WebSocket 扩容；
- 生产级审计、监控、限流和灾备；
- 企业级安全与合规能力。

# Frontend specification

采用单页客服应用布局。

## 顶部栏

包含：

- PineCare 品牌名称；
- “松果商店智能客服”副标题；
- 服务状态，例如“Demo · 使用模拟数据”；
- “新建对话”按钮。

需要始终明确这是演示环境，避免用户把模拟订单当成真实订单。

## 左侧 conversation list

桌面端保留左侧列表，因为它能直观证明对话持久化，也让页面更像完整产品。

列表内容：

- “新建对话”入口；
- 最近对话；
- 会话标题；
- 最后一条消息时间；
- 当前选中状态。

移动端改为抽屉，不长期占用屏幕。不需要搜索、文件夹、删除、归档或无限分页。

## 主聊天区域

### Empty state

新会话尚无消息时显示：

- 简短欢迎语；
- 能力说明；
- 3 个示例问题：“退款多久到账？”、“查询订单 ORD-1001”、“发货后还能改地址吗？”。

### Message bubbles

用户消息：

- 右侧显示；
- 使用明显但不过度鲜艳的品牌色；
- 显示发送时间。

机器人消息：

- 左侧显示；
- 支持普通文本、列表和简单强调；
- 显示 citation、工具结果或 escalation card；
- 不直接渲染不受控制的 HTML。

### Citation

每个知识库回答下方显示 citation chips，例如：

- `退款政策 · 退款到账时间`
- `配送政策 · 修改收货地址`

点击后展开：

- 来源标题；
- 文档分类；
- 命中的短片段；
- 来源 ID。

Citation 不跳到外部网站，因为知识数据在 repo 内。

### Typing/loading

发送后：

- 输入框暂时禁用或防止重复提交；
- 显示“正在查找相关政策…”；
- 如果调用订单工具，可显示“正在查询演示订单…”；
- 等待结束后替换为正式回复。

不要求逐 token 流式输出。

### Escalation card

无法回答时显示卡片：

- 无法可靠回答的说明；
- 机器人生成的工单摘要预览；
- “创建人工工单”按钮；
- “暂不创建”按钮。

创建成功后显示：

- 工单 ID；
- 状态 `Open`；
- 创建时间；
- “这是本地 Demo 工单，不会发送到真实客服”的提示。

### Error state

区分：

- 网络/API 请求失败；
- LLM 服务不可用；
- 回复生成失败；
- 工单创建失败。

错误信息应出现在对应消息位置，并提供“重试”。失败的请求不能生成一条看似成功的机器人回答。

## 输入区域

包含：

- 多行文本输入框；
- 发送按钮；
- Enter 发送、Shift+Enter 换行；
- 空输入不可发送；
- 简短提示：“机器人可能无法处理账户操作，必要时请转人工。”

## Conversation title

标题由首条用户消息确定性生成：

- 去掉多余空格；
- 截取约 20 个中文字符；
- 超长时加省略号；
- 空标题回退为“新对话”。

这比额外调用 LLM 更稳定，也更节省 Demo 时间。

# Backend responsibilities

后端保持为单一应用服务，不拆微服务。

## 最少业务对象

- Conversation
- Message
- KnowledgeSource
- MockOrder
- SupportTicket

不需要单独创建 Citation 表。Citation 是机器人消息生成时保存的结构化元数据。

## 最小 API

### `POST /api/conversations`

创建新会话，返回 conversation ID、标题和创建时间。

### `GET /api/conversations`

返回最近会话列表，按更新时间倒序。

### `GET /api/conversations/{conversationId}`

返回会话信息及消息历史。

### `POST /api/conversations/{conversationId}/messages`

请求包含用户文本。服务内部完成：

1. 保存用户消息；
2. 读取近期上下文；
3. 判断是否需要订单工具；
4. 检索知识库；
5. 生成 grounded response；
6. 验证 citation；
7. 保存机器人消息；
8. 返回回复、引用、工具结果和 escalation 建议。

MVP 可以使用单次 HTTP 请求，不要求流式接口。

### `POST /api/conversations/{conversationId}/tickets`

在用户确认后创建支持工单。请求包括当前问题摘要和可选的关联消息 ID，返回 ticket ID、状态和创建时间。

### `GET /api/health`

供启动检查和端到端测试使用。

## Service responsibilities

后端内部至少包含以下职责边界：

- Conversation service：会话创建、列表和历史读取；
- Message service：消息验证与持久化；
- Retrieval service：索引、检索、排序和置信度判断；
- Chat orchestration：上下文、检索、工具和 LLM 组合；
- Grounding validator：确保引用存在、限制无依据回答；
- Mock order service：读取本地模拟订单；
- Support ticket service：创建本地工单。

这些是代码职责，不要求部署成独立服务。

## 需要持久化的数据

- Conversation；
- 用户和机器人 Message；
- 机器人消息使用的 citations；
- SupportTicket；
- MockOrder 演示数据；
- 知识库索引或可重建的索引状态。

## 可以纯运行时处理的数据

- 当前请求使用的 prompt；
- 临时检索候选；
- 排序分数；
- LLM 原始中间输出；
- tool routing 决策；
- 当前请求组装出的 conversation context。

知识原文由 repo 管理，数据库中的搜索索引可以随时重建。

# Knowledge base specification

## 规模

提供 **24 条 FAQ**，分为 6 个主题，每个主题约 4 条：

1. 退款与退货；
2. 订单取消；
3. 配送与收货地址；
4. Plus 会员；
5. 产品保修；
6. 联系客服与账户操作限制。

24 条足以产生真实检索、相似问题和歧义，又不会让内容维护成为主要工作。

## 文档格式

Repo 中使用 Markdown 或 YAML。推荐每条 FAQ 一个 Markdown 文件，或每个主题一个 Markdown 文件，其中每条政策有稳定 ID。

每条知识条目至少包含：

- `id`
- `title`
- `category`
- `question_variants`
- `content`
- `keywords`
- `updated_at`

示例 ID：

- `refund-arrival-time`
- `change-address-after-shipping`
- `membership-cancellation`
- `warranty-duration`

`updated_at` 是演示内容字段，不需要版本系统。

## 主题内容示例

- 退货申请期限；
- 退款到账时间；
- 原支付方式退款；
- 已拆封商品的退货限制；
- 发货前取消；
- 发货后取消限制；
- 发货前修改地址；
- 发货后修改地址；
- 标准配送时效；
- Plus 会员取消；
- 当前会员周期；
- 会员费用退款条件；
- 一年有限保修；
- 非保修损坏；
- 保修申请所需信息；
- 机器人无法执行的账户操作。

## 检索方案

MVP 使用：

> **SQLite FTS5 lexical retrieval + 中文关键词归一化 + 简单加权排序**

原因：

- 24 条短 FAQ 不需要向量数据库；
- 数据小、查询快、结果稳定；
- 无需额外服务；
- 不依赖首次运行下载 embedding 模型；
- 更容易写确定性检索测试；
- 完全足以演示 retrieval、grounding 和 citation。

排序可以综合：

- 标题命中；
- `question_variants` 命中；
- 正文命中；
- 分类和关键词命中；
- 近期上下文补充的查询词。

维护少量业务同义词，例如：

- “退钱”→“退款”
- “改地址”→“修改收货地址”
- “寄出”→“发货”
- “会员关闭”→“取消会员”

不在 MUST HAVE 中加入 embedding。若时间充足，可将“本地 embedding + lexical 的 hybrid rerank”作为 NICE TO HAVE，但不能引入独立 vector DB。

## Grounding threshold

检索结果分为三个区间：

- 高相关：可以基于来源直接回答；
- 中相关：只能给出有限答案，并追问缺失信息；
- 低相关或无结果：禁止回答业务事实，进入 fallback。

阈值需通过固定测试集校准，而不是只凭主观设置。

## Citation 展示

后端返回结构化 citation：

- `source_id`
- `title`
- `category`
- `snippet`

生成答案后验证：

- `source_id` 必须来自本次检索结果；
- ID 必须在知识库存在；
- snippet 必须取自对应原文；
- 没有实际使用来源时不展示 citation；
- 订单查询结果标记为“演示订单数据”，不伪装成知识库文档。

# Agent behavior contract

机器人必须遵守以下行为契约：

1. **知识优先**：涉及松果商店政策的事实，只能依据本次检索到的知识来源回答；
2. **有限回答**：来源只能支持部分结论时，只回答被支持的部分，并说明缺少什么信息；
3. **不知道就明确说不知道**：没有可靠来源时，不使用常识猜测松果商店政策；
4. **引用必须真实**：不得生成不存在的 source ID、标题或原文片段；
5. **不得伪造订单信息**：只有订单工具返回的数据才能被描述为订单状态；
6. **不得伪造动作结果**：不能声称已经退款、取消订单、修改地址、取消会员或批准保修；
7. **工具边界明确**：`get_order_status` 只查询，`create_support_ticket` 只创建本地演示工单；
8. **账户相关问题升级处理**：需要身份、支付详情或真实账户权限的操作，必须提示转人工；
9. **保护隐私**：不主动索要密码、完整支付卡号或验证码，Demo 仅需演示订单号；
10. **使用近期上下文**：解析“它”“那这个订单”等指代，但不能把上一会话的信息带到新会话；
11. **冲突处理**：用户描述与订单工具数据冲突时，明确区分“你提供的信息”和“演示订单查询结果”；
12. **简洁客服语气**：先直接回答，再补充条件和下一步，避免长篇政策复述；
13. **失败透明**：LLM、检索或工具报错时说明服务暂时失败，不把异常解释为“没有相关政策”。

推荐后端对 LLM 输出做结构化约束，要求返回：

- answer；
- used source IDs；
- tool intent；
- fallback reason；
- escalation suggestion。

最终显示前必须经过服务端验证。

# Tool calling recommendation

建议加入两个本地 fake tool，价值明显且实现规模可控。

## 1. `get_order_status(order_id)`

输入：

- `order_id`

输出：

- 是否存在；
- 商品简述；
- 当前状态；
- 配送状态；
- 是否已发货；
- 预计送达时间；
- 是否允许取消；
- 是否允许修改地址。

准备约 5 个模拟订单：

- `ORD-1001`：已发货，不可直接改地址；
- `ORD-1002`：待处理，可以取消和修改地址；
- `ORD-1003`：已送达，可进入退货政策咨询；
- `ORD-1004`：已取消；
- `ORD-1005`：运输延迟。

订单不存在时不得猜测。

## 2. `create_support_ticket(summary)`

内部还可以接收 conversation ID 和关联 message ID。

输出：

- ticket ID；
- `Open` 状态；
- 创建时间。

该工具必须由用户点击确认后调用，不应仅因为模型建议升级就自动创建工单。

这两个工具让 Demo 形成完整链路：

```text
知识咨询 → RAG 回答
订单问题 → 本地工具查询
无法解决 → 用户确认 → 创建工单
```

值得加入。第三个工具不会带来足够价值，不建议增加。

# Test strategy

## Backend unit tests

覆盖：

- 会话标题生成；
- 消息输入验证；
- 近期上下文选择；
- 订单号解析；
- 模拟订单查询；
- 工单 ID 和状态创建；
- citation 验证；
- 低置信度 fallback；
- 不存在订单的处理。

## Retrieval tests

使用固定知识库和固定查询集验证：

- “退款多久到账”命中退款到账政策；
- “寄出后改地址”命中发货后地址政策；
- “会员不想续了”命中会员取消政策；
- 退款问题不会把保修政策排在首位；
- 完全无关的问题低于回答阈值；
- 同义词归一化有效；
- 多轮补全后的检索优于只使用“那还能改吗”。

测试不只断言“有结果”，还应断言正确 source ID 位于前若干结果。

## Grounded response behavior tests

LLM 层使用可控 fake model 或记录好的结构化输出，以避免测试依赖网络和随机性。

验证：

- 回答只能引用检索结果中的来源；
- 虚构 citation 被拒绝；
- 无来源的政策答案被替换为 fallback；
- 不得声称已执行退款或改地址；
- 订单事实必须来自工具结果；
- 中等相关问题会追问，不会补造条件；
- 需要账户权限时建议转人工。

可以额外保留少量真实模型评估测试，但不能成为默认测试套件的稳定性依赖。

## API integration tests

至少覆盖一个完整链路：

1. 创建会话；
2. 发送退款问题；
3. 收到带 citation 的回答；
4. 重新读取会话；
5. 确认消息已经持久化。

另覆盖模拟订单查询、未知问题产生 escalation 建议，以及用户确认后创建工单。

## Frontend minimal tests

覆盖：

- 空状态和示例问题渲染；
- 发送按钮的禁用与 loading 状态；
- 用户和机器人消息渲染；
- citation 展开；
- escalation card 确认操作；
- API 失败后显示重试按钮。

## End-to-end smoke

浏览器自动执行：

1. 打开首页；
2. 创建新会话；
3. 输入“退款多久到账？”；
4. 等待回答；
5. 检查 citation 可见；
6. 刷新页面；
7. 检查会话和消息仍然存在。

如果时间允许，再增加订单查询链路，但一条稳定 smoke 已满足 MVP。

# Intentional failure/fix scenario

选择：

> **知识库无答案时，机器人不得编造政策。**

测试问题：

> Plus 会员可以共享给五个家庭成员吗？

知识库中没有家庭共享政策。

测试期望：

- 回复明确说明知识库没有该信息；
- 不出现人数、价格或共享规则；
- 返回 escalation 建议；
- citations 为空。

自然的初始失败：

- 初始实现只把最高检索结果交给 LLM；
- 检索器可能返回“Plus 会员取消政策”；
- LLM 根据常识编造一个听起来合理的家庭共享规则；
- 行为测试失败。

合理修复：

1. 引入最低相关度阈值；
2. 要求政策性陈述必须绑定 source ID；
3. 校验 source ID 是否来自本次检索；
4. 没有受支持结论时强制 fallback；
5. 增加该问题作为回归测试。

这是检索、LLM 和产品安全边界之间的真实集成问题，不是人为制造的低级错误。

# Demo questions

| 输入 | 覆盖场景 | 期望行为 |
|---|---|---|
| “退款多久到账？” | FAQ 直接回答 | 返回明确时限，并引用退款到账政策 |
| “商品不合适，我该怎么办？” | 模糊问题 | 给出有限退货规则，并追问签收时间或商品状态 |
| “发货后还能修改地址吗？” | 政策查询 | 说明一般限制，引用地址修改政策，不声称已修改 |
| “我的订单已经发货了。” → “ORD-1001，那还能改地址吗？” | 多轮、工具、检索 | 识别上下文，查订单状态，同时引用政策 |
| “帮我查一下 ORD-1002。” | 订单工具 | 展示待处理状态以及可取消、可改地址信息 |
| “请直接帮我取消 ORD-1002。” | 动作边界 | 说明机器人不能执行取消，建议人工工单 |
| “ORD-9999 到哪了？” | 工具无结果 | 明确订单不存在于演示数据，不编造状态 |
| “Plus 会员可以共享给家人吗？” | 知识库无答案 | 明确不知道，提供转人工入口 |
| “你们明年会在成都开店吗？” | 完全不支持 | 不预测，提供 escalation |
| “我的键盘坏了，能保修吗？” | 部分相关 | 引用保修期限和条件，追问购买时间及损坏类型 |

Demo 页面可以显式展示 `ORD-1001` 和 `ORD-1002` 是可用演示订单号，避免观众不知道如何测试工具能力。

# Definition of Done

产品达到以下全部条件才算完成：

1. Fresh clone 后按照 README 的有限步骤可以本地启动；
2. 不需要外部商业数据库、消息队列或向量数据库；
3. 前端可通过浏览器访问，并有清晰的产品化页面；
4. 用户可以创建新 conversation；
5. 左侧可以看到最近 conversation 和标题；
6. 用户可以发送消息并收到机器人回答；
7. 刷新页面后 conversation 和消息仍然存在；
8. Repo 内至少包含 24 条可读知识条目；
9. “退款多久到账？”能检索到正确来源；
10. 知识库回答至少展示一个真实 citation；
11. Citation 可以展开查看标题和原文片段；
12. 模糊问题得到有限回答或澄清问题，不被过度推断；
13. 不支持的问题不会产生虚构业务答案；
14. 不支持的问题可以显示人工升级卡片；
15. 用户确认后可创建本地支持工单并看到 ticket ID；
16. `ORD-1001` 可以通过订单工具查询；
17. 不存在的订单不会得到虚构状态；
18. 机器人不会声称已经退款、取消订单或修改地址；
19. 多轮示例中，第二条消息能正确利用当前会话上下文；
20. Loading、API 失败和重试状态可以人工触发并观察；
21. 默认自动测试不依赖随机的真实 LLM 输出；
22. 后端单元、检索、行为、API 集成和前端最小测试通过；
23. 端到端 smoke test 通过；
24. README 列出 Demo 问题、模拟订单号、数据重置方式和已知限制。

# Complexity analysis

| 工作域 | 真实工作内容 | 是否足以独立开展 |
|---|---|---|
| product/spec | 明确业务边界、对话流程、失败行为和验收条件 | 是 |
| frontend | 对话列表、消息区、citation、工具结果、工单卡片、错误状态 | 是 |
| backend | Conversation API、消息编排、服务边界和错误处理 | 是 |
| persistence | SQLite 模型、初始化、历史恢复和演示数据 | 是，但规模较小 |
| retrieval | 知识格式、FTS 索引、查询归一化、排序和阈值 | 是 |
| LLM integration | Prompt contract、结构化输出、上下文和 grounding 验证 | 是 |
| tool calling | 意图路由、订单查询、确认后建工单 | 是，但保持两个工具 |
| testing | 确定性 fake、检索回归、行为约束、API、前端和 E2E | 是 |
| integration | 前后端协议、LLM/检索/工具组合、持久化和异常链路 | 是 |
| review | 产品边界、幻觉风险、citation 正确性、UI 可用性和代码质量 | 是 |

没有哪个指定工作域完全没有实际工作。

其中 persistence 和 tool calling 单独看并不庞大，但它们与聊天编排、UI 和测试有真实集成边界。整个产品自然适合多人或多 Agent 分工，不需要人为拆分诸如“写两个按钮”这样的伪任务。

# Estimated implementation difficulty

整体难度：**中等**。

相对难点：

- 检索相关度阈值和 fallback 行为；
- LLM 输出的 grounding 与 citation 校验；
- 多轮上下文、检索和工具结果的组合；
- 让自动测试既验证行为，又不受 LLM 随机性影响；
- 前后端各种状态组合的完整呈现。

相对简单：

- SQLite 数据规模小；
- FAQ 由 repo 自带；
- 订单与工单均为本地模拟；
- 无认证、无权限、无外部客服平台；
- 无生产部署和扩容要求。

预期代码规模应是“小型完整应用”，而不是单文件样例，也不会接近客服 SaaS 平台。

# Recommended final scope

最终建议锁定为：

> 一个单 repo、本地优先的 PineCare 智能客服应用；包含产品化聊天界面、最近对话、SQLite 持久化、24 条 FAQ、FTS 检索、grounded LLM 回答、真实 citation、多轮上下文、模拟订单查询，以及用户确认后创建本地支持工单。

最终只保留两个工具：

- `get_order_status`
- `create_support_ticket`

MUST HAVE 中不加入：

- Authentication；
- 管理后台；
- embedding/vector DB；
- streaming；
- 真实外部 API；
- 工单处理工作台。

如果开发时间紧张，首先放弃 NICE TO HAVE，不削弱 fallback、citation、持久化和测试，因为这四项决定它是不是一个真实可信的客服产品。

# Final judgment

**B. GOOD DEMO SCOPE**

它能让观众在 30 秒内理解产品，在 5 分钟内依次看到知识问答、引用、订单工具、多轮上下文、拒绝编造、人工升级和历史恢复，同时又确实需要前端、后端、数据库、检索、LLM、工具调用、测试与集成协作。

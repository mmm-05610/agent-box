# 正常回执的持续工作项状态

目的：让用户直接知道交付到哪、卡在哪、谁在处理。不是新增看板上报流程。
在**已有普通 outbox 回执或 status.md** 中嵌入下列 `work-status` JSON 块。
可用此块代替原本的“完成/阻塞/下一步”段落，不重复写两份。

## 身份与更新

- 工作项及唯一状态 owner 见 `WORK-ITEMS.json`。同一故障的定位/修复/复验使用同一 work_id。
- owner 正常更新时读取最高 revision，加一；完整替换该项状态，不只写变化片段。
- I 已根据具名证据登记 r0，后续由目录指定 owner 写 r1 起；他人可交证据但不可覆盖其状态。
- 纯 ACK 不必更新。阶段变化、遇新阻塞、交付/复验完成时随正常回执更新，不另发看板文件。
- 普通文字仍自动可见；有更新交互但无本项状态时会提示待同步，不猜测执行状态。
- 同 revision 不同内容显示冲突；无效块显示错误，不静默覆盖。时间戳不决定裁定胜负。
- C 负责维护工作项目录及集成验收项，不抄录每个执行者状态。新模块/任务在目录登记后即可增量纳入。

## 字段示例（仅格式示例，不是当前项目事实）

```work-status
{
  "work_id": "SESSION-DESKTOP",
  "owner": "FC",
  "revision": 1,
  "state": "diagnosing",
  "done": "已能打开会话，后端首条执行完成。",
  "problem": "界面未显示首条回复，第二条未发送。",
  "action": "核对事件流到消息列表的投影。",
  "waiting_for": "无",
  "next": "定位最小修复并跑定向反例，再复验两轮。",
  "acceptance": "同一会话在桌面显示两次真实回复。",
  "evidence": "agents/FC/outbox/具体回执.md，实际测试记录路径"
}
```

state 取 working/diagnosing/fixing/waiting/retest/verified/blocked/not_started/review。
verified 只表示该项指定范围有验收证据，不代表主线或用户体验自动通过。
problem/action/next 用短句、用户能理解的现象与动作；不要只写 SHA、批号、READY 或英文合同名。
没有问题写“无”；没有执行中的动作如实写“暂无在途动作”，不要用计划冒充正在跑。
evidence 可写较长精确路径，默认只在详情显示。不得放凭据、配置正文、原始私有日志。

## 不改变的边界

用户决策继续原队列；此状态块不授予实施/调用权限。中央继续监督及时升级阻塞。
不为同步看板重启会话、不新增 watcher、不做额外模型调用，不阻塞正在进行的产品修复。
